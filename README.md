# RE_CONNECT — 다시잇다

2026 제13회 소프트웨어(SW) 개발보안 경진대회(트랙 C · 공공활용 부문) 출품작 저장소입니다.

**다시잇다**는 공백기를 거친 시니어가 대화로 자신의 경험과 희망을 정리하고, 취업·봉사·멘토링·지역활동·교육 기회를 한곳에서 비교해 공식 신청까지 이어가도록 돕는 서비스입니다. 경력·생활 조건 같은 개인정보와 LLM을 함께 다루기 때문에, **보안은 마지막에 점검하는 항목이 아니라 설계 단계의 요구사항**으로 둡니다.

> 기획 원문: [다시잇다_개발기획서_수정.pdf](다시잇다_개발기획서_수정.pdf)

## 1. 핵심 기능

| ID | 기능 | 요약 |
| --- | --- | --- |
| F1 | 대화형 프로필 추출 | 대화에서 경험·시간·이동범위·목적을 LLM이 JSON으로 구조화하고, 사용자가 수정·확정 |
| F2 | 경험 → 역할 매핑 | 직함을 작업·기술·관계 역량으로 분해해 역할 후보 2~4개와 근거 제시 |
| F3 | 통합검색·랭킹 | 기관별 공고를 공통 스키마로 정규화, 필터 + 키워드·의미 검색 |
| F4 | 추천 근거 설명 | 확정 프로필과 공고 원문의 사실만으로 "맞는 이유 / 안 맞는 조건 / 확인 필요" 분리 |
| F5 | 자격조건 검증 | 명시 조건만 대조해 지원 가능 / 미충족 / 확인 필요 3단계 표시 (추정 금지) |
| F6 | 신청지원·문서작성 | 준비서류 체크리스트, 사용자가 승인한 사실만으로 지원서 초안 생성 (대리 제출 없음) |

## 5. 보안 개발 진행 방식

### 5.1 원칙

1. **설계에서 시작** — 기능을 만들기 전에 진단가이드의 설계단계 기준(입력데이터 검증, 보안기능, 에러처리, 세션통제)으로 위협을 먼저 정리한다.
2. **약점 단위로 추적** — 모든 보안 관련 작업은 KISA 보안약점 이름으로 이슈·PR·테스트에 연결한다.
3. **비신뢰 데이터 원칙** — 사용자 입력, 외부 공고 원문, LLM 출력은 모두 비신뢰 데이터로 다룬다.
4. **최소 수집·최소 전달** — 필요한 개인정보만 저장하고, LLM에는 기능에 필요한 최소·가명 정보만 보낸다.
5. **증명 가능한 보안** — "적용했다"가 아니라 "이 테스트로 막히는 것을 확인했다"를 남긴다.

### 5.2 기능 하나를 개발하는 흐름

```
① 착수        INDEX "다시잇다 기능별 탐색"에서 해당 기능의 관련 약점 확인
               → 이슈에 체크리스트로 붙임
② 설계        진단가이드 설계단계 기준으로 입력·인증/인가·에러·세션 요구사항 정리
③ 구현        Python 가이드의 "안전한 코드 예시"를 기준으로 작성
④ 테스트      약점별 공격 시나리오를 Pytest로 작성 (정상 + 공격 입력)
⑤ 자동 점검   Bandit(코드), pip-audit(의존성) 통과
⑥ 리뷰        PR에 대응 약점·테스트를 명시하고 보안 담당 리뷰 후 병합
⑦ 기록        발견·조치 내용을 docs/security/ 진단 기록에 남김
```

### 5.3 기능·영역별 중점 보안약점

기획서 2.5절의 위험 지점과 볼트의 기능별 탐색표를 합친 것입니다. 각 약점의 원문은 INDEX.md에서 이름으로 찾습니다.

| 영역 | 중점 보안약점 (KISA) | 적용 통제 | 검증 시나리오 |
| --- | --- | --- | --- |
| 인증·세션·권한 | 적절한 인증 없는 중요 기능 허용, 부적절한 인가, 반복된 인증시도 제한 기능 부재, 잘못된 세션에 의한 데이터 정보 노출 | 안전한 비밀번호 해시, Secure·HttpOnly·SameSite 쿠키, 프로필 소유권 확인, 관리자 역할 분리, 로그인 실패 제한 | 타 사용자 프로필 조회, 관리자 권한 우회, 반복 로그인 |
| DB 접근 | SQL 삽입, 부적절한 인가 | SQLAlchemy ORM 바인딩, 사용자 범위 쿼리 강제 | SQLi 페이로드, 다른 사용자 ID로 요청 |
| 화면 출력·외부 공고 | 크로스사이트 스크립트, 크로스사이트 요청 위조, 신뢰할 수 없는 데이터의 역직렬화 | 출력 이스케이프, CSRF 토큰, CORS 허용 목록, Pydantic 검증 | XSS 공고 문구, CSRF 요청, 비정상 형식 입력 |
| 공고 수집·외부 URL | 서버사이드 요청 위조, 신뢰되지 않은 URL 주소로 자동접속 연결, 부적절한 인증서 유효성 검증 | 외부 URL 허용 목록, 리다이렉트 검증, TLS 검증 강제 | 내부 주소로의 SSRF, 오픈 리다이렉트 |
| 프로필·LLM 연동 | 암호화되지 않은 중요정보, 하드코드된 중요정보, 오류 메시지 정보노출 | 마스킹 후 LLM 전달, 비밀값은 환경변수·비밀관리 저장소, 구조화 출력 검증 | 로그·응답 내 개인정보 검색, 비밀값 노출 점검 |
| 지원서 초안 암호화 | 취약한 암호화 알고리즘 사용, 충분하지 않은 키 길이 사용, 솔트 없이 일방향 해시 함수 사용 | AES-256-GCM, 키 분리 보관 | 알고리즘·키 길이 코드 점검 |
| 요청 제한 | 반복된 인증시도 제한 기능 부재, 종료되지 않는 반복문 또는 재귀 함수 | Redis Rate Limit, LLM 호출 상한, 요청 크기 제한 | 과대 요청, 대량 호출 |
| 로그·예외 | 오류 메시지 정보노출, 오류상황 대응 부재, 부적절한 예외 처리 | 대화 원문·개인정보 로그 금지, 공통 예외 핸들러 | 오류 유발 후 응답·로그 확인 |
| 파일·인프라 | 경로 조작 및 자원 삽입, 중요한 자원에 대한 잘못된 권한 설정, 운영체제 명령어 삽입 | 경로 정규화, 최소 권한 컨테이너, 셸 호출 금지 | 경로 탐색 입력, 명령어 삽입 입력 |
| 삭제·동의 철회 | 암호화되지 않은 중요정보, 부적절한 인가 | 동의 버전 관리, 삭제 요청 처리·기록 | 삭제 후 재조회, 백업 복구 확인 |

**가이드에 독립 항목이 없는 위험** — 아래는 KISA 가이드 밖이라 별도로 기준을 정하고 테스트합니다.

- **프롬프트 인젝션**: 공고 원문은 도구 입력으로 격리하고 명령으로 취급하지 않음, 외부 발송·파일 접근 도구 금지, 악성 공고 지시문 샘플 테스트
- **LLM 호출 비용 상한**: 사용자·세션별 호출 횟수 제한
- **동의·보관기간·삭제 정책**: 개인정보보호위원회 생성형 AI 안내서 등 별도 기준 참고

## 7. 협업 규칙

### 브랜치

- `main` — 항상 실행 가능한 상태. 직접 push 금지, PR로만 병합
- `feat/<기능>` · `fix/<내용>` · `sec/<약점>` · `docs/<내용>`

### 커밋 메시지

```
feat: F1 대화 세션 API 추가
sec: 프로필 조회 소유권 검증 (부적절한 인가)
docs: 위협 모델 초안
```

### PR 체크리스트

```markdown
- [ ] 관련 KISA 보안약점: (예: SQL 삽입, 부적절한 인가)
- [ ] 해당 약점의 공격 시나리오 테스트 추가
- [ ] Bandit / pip-audit 통과
- [ ] 비밀값·개인정보가 코드·로그·커밋에 없음
- [ ] 사용자 입력·공고 원문·LLM 출력을 비신뢰 데이터로 처리
```

### 절대 커밋하지 않는 것

`.env`, API 키, 인증서·개인키, 실제 사용자 데이터, 인터뷰 원본. 실수로 올렸다면 삭제 커밋만으로는 부족하니 **키를 즉시 폐기·재발급**하고 팀에 알립니다.
