# 다시잇다 프론트 완성 계획

작성일: 2026-10-29

상태: 실행 전 계획. 이 문서 작성으로 화면이나 기능이 완성된 것은 아니다.

이 계획은 현재 프론트 코드와 사용자가 화면을 수정하며 정한 기준을 바탕으로 한다. [기존 개편 계획](07_Frontend_Redesign_Plan.md)의 후속 실행 기준이며, 과거 디자인 제안과 충돌하는 부분은 최근 사용자 요청을 따른다. 새로운 기능을 계속 늘리기보다 지금 약속한 이용 흐름을 완성한다.

실행할 때는 [스타일 보존 기준](../frontend/DESIGN_BASELINE.md)과 [실행 준비서](09_Frontend_Execution_Runbook.md)를 함께 읽는다. 사용자 요청을 수치와 재사용 코드, 현재 캡처에 연결했으며, 캡처 속 결함을 보존 대상으로 삼지 않는다.

## 1. 이번 작업의 끝

아래 두 흐름을 개발용 화면 이동 메뉴 없이 이용할 수 있게 한다.

1. 공고부터 보기 → 전체 공고 → 상세 → 공식 신청 안내
2. 경험 이야기 → 내 경험 확인과 수정 → 확정 → 추천 → 상세와 조건 대조 → 지원서 작성과 검토 → 공식 신청 안내

경험과 지원서를 보관하려는 사용자는 해당 화면에서 저장을 선택한다. 로그인과 저장 동의를 거쳐 저장한 뒤, 내 자료에서 다시 열고 수정하거나 삭제할 수 있어야 한다.

완료는 세 단계로 구분한다.

| 단계 | 충족해야 하는 조건 |
| --- | --- |
| 화면 완성 | 정상 화면뿐 아니라 빈 상태와 처리 중, 오류, 긴 내용에서도 읽고 조작할 수 있다. 아래 디자인 기준을 모두 충족한다. |
| 기능 연결 완료 | 예시 자료가 아닌 서버 응답으로 핵심 흐름을 수행한다. 실패나 취소를 성공으로 표시하지 않는다. |
| 배포 준비 완료 | 실제 AI와 인증, 저장 왕복 및 대상 브라우저를 확인한다. 필요한 운영 안내가 게시되어 있다. 확인하지 못한 항목이 없거나 배포를 막는 조건으로 명시되어 있다. |

화면이 보인다는 이유로 기능 연결 완료를 표시하지 않는다. 검사 통과만으로 실제 이용 완료를 표시하지 않는다.

## 2. 모든 화면에 적용할 원칙

### 문구

- 직접 작성하는 화면 제목과 버튼, 메뉴, 안내에 가운데 점을 사용하지 않는다. 짧은 단어 하나로 바꾸거나 자연스러운 문장으로 쓴다.
- 한 작업에 같은 이름을 사용한다. 경험, 공고, 지원서, 저장의 명칭을 화면마다 바꾸지 않는다.
- 제목으로 알 수 있는 내용을 설명에서 반복하지 않는다.
- 사용자가 지금 판단하거나 행동하는 데 필요한 안내만 남긴다. 기능 소개, 내부 처리 설명, 개발 상태, 버전 번호를 기본 화면에 반복하지 않는다.
- 버튼에는 실제 결과를 쓴다. 무엇을 하는지 알 수 없는 '확인', '다음'만 단독으로 쓰지 않는다.
- 성공 문구는 실제 결과를 확인한 뒤 표시한다. 입력 화면에서만 바뀐 내용을 서버에 저장했다고 표현하지 않는다.
- 동의 내용, 개인정보 처리 범위, 삭제 영향, 외부 신청 안내처럼 행동에 필요한 내용은 해당 행동 직전에 제공한다. 간단하게 만든다는 이유로 의미를 없애지 않는다.
- 공식 공고와 게시 안내문 원문을 임의로 바꾸지 않는다. 원문은 필요한 위치에서 확인할 수 있게 제공한다.

### 정보량

- 기본 화면은 제목 하나, 현재 작업 하나, 가장 중요한 행동 하나를 중심으로 구성한다.
- 보조 행동은 기본적으로 두 개 이내로 정리한다. 나머지는 편집 상태나 관련 행동을 선택했을 때 제공한다.
- 제목 아래 설명이 필요하면 한 문장부터 검토한다. 긴 소개 문단을 기본값으로 넣지 않는다.
- 공고 목록은 제목과 기관, 판단에 필요한 핵심 정보 2~3개를 먼저 보여준다. 상세 조건과 긴 설명은 상세 화면에서 보여준다.
- 같은 정보를 요약 카드, 안내 상자, 본문에서 반복하지 않는다.
- 패널 안에 패널을 계속 넣지 않는다. 주 작업 영역 하나와 간격, 구분선으로 정리한다.
- 정보가 많으면 중요도가 낮은 설명을 먼저 줄인다. 필요한 사실이나 사용자 입력을 잘라내지 않는다.

### 크기와 배치

- 기본 검수 화면은 1280×650 CSS px이다. 1440×800과 1920×1080에서도 배치를 확인한다.
- 기본 상태의 제목, 핵심 입력이나 판단 정보, 주요 버튼은 가능한 한 첫 화면 안에 표시한다.
- 모든 주요 라운드 박스는 공통 최대 너비 1120px과 모서리 반경 24px을 따른다. 화면 하나만 별도 높이와 너비로 커지지 않게 한다.
- 모바일은 양쪽 여백 16px과 모서리 반경 18px을 기준으로 한다.
- 내용이 짧은 기본 화면은 공통 높이와 비율을 맞춘다. 긴 지원서와 공식 원문, 큰 글씨, 확대 상태는 필요한 만큼 페이지가 늘어나게 한다.
- 한 화면에 넣기 위해 글자를 줄이거나 버튼을 작게 만들지 않는다. 겹침, 내용 잘림, 가로 스크롤도 허용하지 않는다.
- 작은 카드 내부 스크롤과 바깥 페이지 스크롤이 경쟁하는 구성을 피한다. 긴 내용은 페이지에서 자연스럽게 읽는다.
- 제목, 입력, 버튼의 위치를 같은 종류의 화면끼리 맞춘다. 주요 버튼을 내용이 바뀔 때마다 다른 곳으로 옮기지 않는다.

### 시니어 이용

- 기존 S-Core Dream과 청색 중심 디자인을 유지한다. 새 테마나 장식 체계를 추가하지 않는다.
- 본문과 중요한 입력 문구는 18px 이상을 기준으로 한다. 주요 버튼 높이는 56px, 나머지 조작 영역은 44px 이상을 확보한다.
- 큰 글씨 보기와 브라우저 200% 확대에서도 읽기와 조작이 유지되어야 한다.
- 기본 대비를 확인하고, 색상만으로 선택이나 오류를 전달하지 않는다.
- 음성과 글 입력을 모두 제공한다. 마이크 권한 거부나 음성 처리 실패 시 글 입력으로 계속할 수 있게 한다.
- 기술 용어 대신 사용자가 이해할 수 있는 말을 쓴다. 한 번에 여러 질문을 하거나 불필요한 개인정보 입력을 요구하지 않는다.
- 키보드 순서와 초점 표시를 유지한다. 화면이나 확인 창이 바뀌면 현재 작업을 찾을 수 있는 위치로 초점을 옮긴다.
- 확인 창은 내용 교체, 삭제, 최종 검토처럼 필요한 순간에만 사용한다. 일반적인 이동과 조회에 확인을 반복하지 않는다.

## 3. 지금까지 요청한 화면 보존 기준

### 첫 화면

- 다운로드 폴더에서 가져온 소개 영상을 사용한다.
- 원본 영상은 제목과 버튼에 닿지 않는 크기로 실제 축소한다.
- 라운드 박스의 나머지 영역은 같은 영상을 확대하고 흐리게 처리해 채운다. 원본과 배경의 재생 위치를 맞춘다.
- 축소 영상의 가장자리는 부드러운 페이드로 배경에 이어지게 한다. 작은 영상 사각형의 경계가 뚜렷하게 보이지 않아야 한다.
- 제목은 위쪽과 왼쪽, 버튼은 아래쪽과 오른쪽으로 배치하되 모서리의 안전 여백을 둔다.
- 원본 영상이 제목이나 버튼을 침범하지 않아야 한다. 그 주변에는 흐린 배경이 닿도록 한다.
- 다른 페이지와 같은 바깥 박스 크기를 사용한다. 영상 배치를 위해 박스 자체를 키우지 않는다.
- 소리가 있는 자동 반복 재생을 유지한다. 재생 바와 멈춤 버튼을 다시 추가하지 않는다. 브라우저가 소리 있는 자동 재생을 막으면 첫 사용자 조작 뒤 재생을 시도하는 실제 동작을 확인한다.

### 공고 탐색

- '일단 둘러볼래요'는 검색 조건 없는 전체 공고 목록으로 이어진다.
- 지도 화면 아래에 결과 영역을 추가하고 강제로 스크롤하는 방식으로 처리하지 않는다.
- 전체 공고와 조건 검색 결과는 같은 목록 구조를 사용한다. 조건 선택과 결과 목록은 화면 상태를 전환해 보여준다.
- 목록에서 상세를 보고 돌아오면 목록의 검색 조건과 페이지를 유지하는 방향으로 구현한다. 검색어와 개인 자료를 불필요하게 영구 저장하지 않는다.

### 지원서

- 첨부 화면에 있던 프로필 참고 정보 상자와 예시 프로필 설명을 기본 작성 화면에서 제거한다.
- 별도의 중간 설명과 버튼을 늘리지 않고, 준비된 초안을 자기소개와 지원동기 입력란에 직접 채운다.
- 사용자는 채워진 내용을 바로 수정하고 최종 검토할 수 있어야 한다.
- 실제 AI 생성과 개발용 예시 문구를 혼동하지 않게 한다. 예시를 채운 것을 AI 생성 성공으로 표시하지 않는다.

## 4. 현재 확인한 기능 차이

2026-10-29의 라우트와 제품 코드 기준이다. 과거 진행 문서의 완료 표시는 현재 연결 상태를 대신하지 않는다.

| 영역 | 확인한 현재 상태 | 완성에 필요한 일 |
| --- | --- | --- |
| 경험 확인 | 편집 기능은 남아 있지만 프로필 주소가 추천 화면으로 이동한다. | 실제 편집과 확정 흐름을 다시 연결한다. |
| 추천 이유와 조건 대조 | 조건 대조 컴포넌트는 있지만 실제 상세 흐름에 연결되어 있지 않다. | 추천 근거와 개인 조건 대조를 공고 상세에 배치한다. |
| 지원서 생성 | 실제 서버는 AI로 확정 사실을 선택하고 고정 형식으로 자기소개를 구성한다. 지원동기는 비워 둔다. 개발 예시 화면은 준비된 문구를 넣는다. | 사용자가 확인한 사실에 근거한 자기소개와 지원동기 문장 생성 기능을 구현하고 작성 화면과 연결한다. |
| 저장 | 관련 컴포넌트는 있지만 현재 저장 주소가 추천 화면으로 이동한다. | 저장 선택, 로그인 복귀, 동의, 결과를 실제 이용 흐름에 연결한다. |
| 나의 정보 | 예시 회원 정보를 화면 안에서 편집한다. | 실제 계정 상태와 필요한 관리 기능을 보여준다. |
| 나의 이야기 | 고정된 예시 경험을 보여준다. | 저장한 확정 프로필을 조회하고 수정이나 재사용으로 연결한다. |
| 저장한 공고 | 예시 공고 카드 목록이다. | 이번 핵심 범위에서는 저장한 경험과 지원서를 제공한다. 관심 공고 저장은 별도 서버 기능이 필요하다. |
| 뒤로가기 | 상단 링크가 첫 화면으로 연결된다. | 각 과업의 이전 화면으로 돌아가게 한다. |

## 5. 구현 순서와 단계별 완료 조건

### 1단계. 공통 틀과 이동 정리

화면을 추가하기 전에 공통 박스 크기, 제목 위치, 버튼 크기와 간격, 오류 위치를 고정한다. 실제 이용 경로와 개발용 예시 경로를 구분한다. 사용자가 보던 맥락으로 돌아가는 이동을 정리한다.

완료 조건:

- 첫 화면, 대화, 공고 목록, 지원서, 회원 화면의 공통 박스가 같은 기준을 따른다.
- 뒤로가기가 공고 상세에서는 목록으로, 지원서에서는 선택한 공고로 이어진다. 직접 주소로 들어온 경우에도 돌아갈 위치가 있다.
- 개발용 화면 번호와 이동 메뉴가 없어도 두 핵심 흐름을 이용할 수 있다.
- 잘못된 주소, 자료가 없는 진입, 로그인 필요 상태에서 다음 행동을 제공한다.

### 2단계. 내 경험 확인과 수정

기존 JourneyProfile과 관련 편집 기능을 재사용한다. 대화 뒤에 경험 요약을 확인하고 필요한 내용을 같은 화면에서 수정할 수 있게 한다. 희망 지역과 활동 유형을 확인한 뒤 사용자가 확정한다.

완료 조건:

- AI가 정리한 내용이 틀렸을 때 사용자가 직접 수정하거나 삭제할 수 있다.
- 초기 요약에서 모든 편집 필드와 관리 기능을 한꺼번에 펼치지 않는다.
- 확정 전 수정과 확정된 자료를 구분한다. 반영하지 않은 입력이 있으면 처리 방법을 명확히 제공한다.
- 확정한 내용으로 추천받는다. 역할 후보와 제외는 같은 과업 안에서 제공하고 별도 필수 화면을 만들지 않는다.
- 내용이 바뀌었을 때 이전 추천과 지원서의 재확인 필요 상태가 유지된다.

### 3단계. 공고 목록과 상세 연결

전체 공고와 추천 공고는 같은 목록 컴포넌트를 사용한다. 추천 이유와 개인 조건 대조는 공고 상세에서 확인한다. 원문과 필수조건, 접수 방법을 유지하면서 반복 설명을 줄인다.

완료 조건:

- 전체 공고 조회와 조건 검색, 추천 결과가 각각 어떤 자료인지 알 수 있다.
- '맞는 이유', '맞지 않는 조건', '확인이 필요한 조건'을 짧고 구체적으로 구분한다.
- 개인 조건이 없으면 확인이 필요하다고 표시한다. 지원 가능 여부를 추정하지 않는다.
- 상세에서 목록으로 돌아오면 이전 탐색 맥락을 유지한다.
- 공고 마감, 변경 검토, 조회 실패, 결과 없음에서도 다음 행동을 제공한다.
- 공고를 먼저 둘러본 사용자도 AI 이용 없이 공식 신청 안내를 볼 수 있다.

### 4단계. 지원서 작성과 최종 검토

개발 예시와 실제 작성 화면의 디자인을 하나로 맞추고 실제 경로를 기준으로 완성한다. 작성 시작 행동에서 AI 생성을 요청하고 같은 화면에서 진행 상태와 결과를 보여준다. 초안이 준비되면 두 입력란에 채운다.

서버 선행 작업:

- 확정 프로필과 검수된 공고에 근거해 자기소개와 지원동기 문장을 생성하도록 생성 계약과 검증을 확장한다.
- 없는 경력과 자격, 사용자가 말하지 않은 개인 사정이나 동기를 사실처럼 만들지 않는다. 지원동기는 사용자가 고쳐 확인할 제안 문구로 다룬다.
- 필요한 최소 정보만 사용하고, 공고 원문과 사용자 자료의 지시문을 실행하지 않는다. 생성 결과는 검증한 뒤 화면에 표시한다.
- 기존 동의와 소유권, 버전, 요청 중복 방지, 취소와 늦은 응답 차단을 유지한다.

화면 완료 조건:

- 기본 화면은 선택한 공고, 자기소개, 지원동기, 검토 행동이 중심이다.
- 생성 실패 시 입력을 보존하고 재시도 또는 직접 작성으로 이어진다. 예시 문구를 대신 넣어 성공 처리하지 않는다.
- 다시 생성할 때 이미 수정한 내용을 자동으로 덮어쓰지 않는다.
- 최종 검토는 확인 창이나 같은 화면의 검토 상태로 제공한다. 전체 내용을 읽고 수정 화면으로 돌아갈 수 있다.
- 문서 다운로드와 복사, 공식 신청 안내가 실제 내용과 연결된다. 개발용 다운로드 코드만으로 실제 경로 구현 완료를 표시하지 않는다.
- 공식 신청처 이동을 실제 제출 완료로 표시하지 않는다.

### 5단계. 저장과 다시 이용

저장은 경험 확인 화면과 지원서 검토 화면에서 선택한다. 기존 BeginSave와 PendingSave, 저장 자료 컴포넌트를 검토해 재사용한다. 저장을 위한 설명 화면을 여러 장 새로 만들지 않는다.

완료 조건:

- 확정 프로필과 승인한 지원서만 사용자가 선택해 저장한다.
- 로그인과 저장 동의를 구분한다. 로그인만으로 자료가 저장되지 않는다.
- 로그인 취소와 실패, 기존 저장본 교체, 일부만 저장된 상태를 정확히 처리한다.
- 저장 성공 뒤 내 자료에서 실제 저장본을 확인할 수 있다.
- 저장한 경험과 지원서 목록, 지원서 상세를 제공한다. 수정과 삭제, 재사용이 연결된다.
- 빈 목록에는 시작 행동 하나를 제시하고 예시 회원 자료를 실제 자료처럼 표시하지 않는다.

### 6단계. 계정 관리와 예외 상태 정리

나의 정보는 실제 로그인 상태와 계정 관리 기능을 보여준다. 계정 관리 컴포넌트에 있는 동의 철회와 로그아웃, 탈퇴 기능을 현재 디자인에 연결한다. 이름과 전화번호 등 필요성이 확인되지 않은 개인정보를 새로 수집하지 않는다.

완료 조건:

- 실제 회원 자료와 예시 값을 구분하고 고정된 홍길동 정보를 제거한다.
- 동의 상태를 확인하고 필요한 항목을 관리할 수 있다.
- 로그아웃, 저장 자료 삭제, 동의 철회, 탈퇴의 영향과 결과를 구분한다. 민감한 조작은 관련 설정에서 선택한 뒤 확인한다.
- 로그인 복귀, 세션 만료, 체험 만료, 삭제 실패에서 이용자가 다음 행동을 고를 수 있다.
- 개인정보 처리와 운영 문의 안내는 필요한 위치에서 접근할 수 있다. 게시되지 않은 운영 안내를 임의로 완성하거나 우회하지 않는다.

### 7단계. 전체 문구와 실제 이용 검수

앞 단계에서 바뀐 화면만이 아니라 두 핵심 흐름을 처음부터 끝까지 연결해 확인한다. 화면마다 다른 표현과 크기, 예시 자료의 잔여 표시, 불필요한 중간 단계를 정리한다.

완료 조건:

- 아래 최종 확인표를 모두 확인한다.
- 새 요청이나 중대한 사용성 문제 없이 미관 취향만으로 전체 구성을 다시 바꾸지 않는다.
- 기능상 남은 문제가 있으면 해당 단계만 다시 연다. 이미 확인한 화면은 변경 영향이 있는 범위만 재확인한다.
- 현재 화면 목록과 서비스 안내 문서를 실제 라우트에 맞게 갱신한다.

## 6. 필요한 화면과 상태

주소 수를 늘리는 것을 목표로 삼지 않는다. 독립된 목적이 있는 화면과 같은 화면의 상태를 구분한다.

| 독립 화면 | 같은 화면에서 처리할 상태 |
| --- | --- |
| 첫 화면 | 영상 준비와 재생 |
| 시작 안내 | 동의 확인과 실제 체험 생성 |
| 경험 이야기 | 음성이나 글 입력, 전사 수정, 답변 확인, 처리 실패 |
| 내 경험 확인 | 요약, 수정, 확정, 역할 선택 |
| 공고 목록 | 전체 보기, 조건 선택, 검색 결과, 추천 결과, 결과 없음 |
| 공고 상세 | 추천 이유, 개인 조건 대조, 신고, 마감과 변경 |
| 지원서 작성 | 초안 생성, 직접 작성, 수정, 최종 검토, 내보내기, 저장 시작 |
| 로그인 복귀 | 성공 확인, 취소, 실패, 만료 |
| 내 자료 | 저장 경험과 지원서 목록, 자료 없음 |
| 저장 지원서 상세 | 조회, 편집, 재검토 필요, 삭제 확인 |
| 계정 설정 | 동의, 로그아웃, 삭제와 탈퇴 확인 |

내 자료와 계정 설정은 현재 회원 메뉴 안에서 찾기 쉽게 연결한다. 이름만 다른 중복 페이지를 만들지 않는다.

## 7. 이번 완성 범위에서 추가하지 않을 기능

- 기관 회원가입과 기관용 신청 접수
- 외부 기관 자동 제출과 대리 로그인
- 실제 접수를 확인할 근거가 없는 지원 완료 판정과 지원 현황 관리
- 별도 알림 센터와 복잡한 대시보드
- 핵심 흐름에 필요하지 않은 추가 온보딩과 기능 소개 화면
- 관심 공고 찜하기의 신규 서버 기능

관심 공고는 현재 예시 화면이 있지만 실제 저장 기능과 API가 확인되지 않았다. 이번에는 저장한 경험과 지원서 재사용을 완성한다. 찜하기를 이번 범위에 포함하려면 별도 기능으로 명시해 범위를 변경하고, 미구현 버튼을 기본 화면에 남겨 두지 않는다.

운영자 화면은 기존 공고 검수와 신고, 수집 상태 기능을 유지한다. 핵심 이용 흐름을 완성하는 동안 운영자 대시보드 전면 개편을 추가하지 않는다. 핵심 흐름을 막는 운영 기능은 필요한 범위만 수정한다.

## 9. 검사와 완료 보고 방식

이 계획 작성 단계에서는 테스트를 실행하지 않는다.

구현 중에는 변경한 기능과 직접 관련된 검사부터 실행한다. 같은 실패를 원인 분석 없이 반복하지 않는다. 환경 문제는 원인과 미확인 범위를 남기고 무리하게 환경을 재구축하지 않는다. 전체 테스트와 E2E는 명시적 요청 또는 릴리스 검증 단계에서만 실행한다.

각 단계의 결과는 다음 다섯 가지로 짧게 기록한다.

1. 바꾼 화면과 사용자가 할 수 있게 된 일
2. 예시 화면인지 실제 API에 연결된 화면인지
3. 실행한 검사와 확인한 브라우저 크기
4. 실제 AI와 인증, 저장에서 확인하지 못한 부분
5. 남은 완료 조건과 다음 단계

브라우저 검수는 정상 화면만 확인하지 않는다. 빈 상태와 처리 중, 오류, 긴 내용, 큰 글씨를 확인한다. 가상 응답으로 배치를 확인한 결과와 실제 서버 왕복 결과를 구분한다. 실제 모바일 기기와 스크린리더, 시니어 사용자 확인을 수행하지 않았다면 그렇게 기록한다.

## 11. 실행 중 기록 (2026-10-29)

- 1단계 진행 중: 홈 영상 크기와 패널 너비, 개발 메뉴 배치를 조정하고 뒤로가기의 이력을 연결했다. 실제 브라우저 1280×650 CSS px에서 홈 패널 너비 1120px, 버튼 하단 550px을 확인했다. 첫 진입 시 소리 있는 자동 재생은 차단됐고 사용자 조작 후 재생됨을 확인했다. 다른 크기와 확대, 키보드 확인은 남았다.
- 2단계 진행 중: 대화 완료 행동을 경험 확인 화면에 연결하고 체험 프로필 경로의 추천 리다이렉트를 제거했다. 실제 서버 왕복과 편집·확정은 미확인이다.
- 3단계 진행 중: 조건 검색도 지도 대신 결과 화면으로 전환한다. 1280×650 브라우저에서 서버 오류와 조건 선택 복귀를 확인했다. 8000 포트에 서버 리스닝이 없어 정상 검색과 개인 대조는 미확인이다.
- `npm run typecheck`, `npm run ui:copy` 통과. 관련 테스트 3개 파일 중 공고 카탈로그 테스트는 통과했고 대화와 프로필 테스트에서 24개 실패, 전체 48개 중 24개 통과했다. 확인된 실패에는 현재 화면의 제목·버튼 문구와 과거 기대값의 불일치가 있다. 나머지 실패 원인과 기능은 아직 검증하지 않았다. 전체 테스트와 E2E는 실행하지 않았다.
- 4~7단계, 실제 AI 생성과 인증·저장 왕복, 모바일·확대·키보드 검수는 아직 수행하지 않았다. 각 단계는 완료가 아니다.
