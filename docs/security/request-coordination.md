# 중복 요청과 리비전 경계 (W03-05)

## 구현과 연결 지점

`app.modules.requests`는 단일 Redis에서 예약·진행·완료 재송신, 임시 자원
리비전 CAS, 자원별 요청 키 삭제를 제공한다. `main.py`가 구성한
`app.state.request_service`를 업무 서비스에서 사용한다. Redis 설정·접속 실패는
503이며 프로세스 메모리로 대체하지 않는다.

운영 업무 라우터 연결은 #36/#37/#67/#68/#74에서 수행한다. 이 변경은 실제 업무
API·모델 호출·저장 API가 완성됐다는 증거가 아니다. 실제 Redis와 시험 전용
HTTP 경로로 제어 동작을 확인한다. 이슈 #24의 상태를 배포 통과로 변경하지 않는다.

라우터는 CSRF·세션·동의·소유권을 확인한 뒤 `idempotency_key(request)`로 단일
UUID 헤더를 받고, 서버가 정한 API 이름과 인증된 주체로 `RequestScope`를 만든다.
임시 체험은 `resource_id=journey_id`로 구분한다. 대상 초안 ID 등 하위 자원 참조,
파일 해시, 기준 저장 버전 등 실행을 바꾸는 모든 값은 **검증된 입력 모델**의
JSON dump에 포함한다. 입력 순서만 다른 JSON 객체는 같은 해시이며 값의 타입은
구분한다. `base_revision`은 서비스가 해시에 추가한다. 원문·파일·응답 본문을
기록하지 않으며 해시도 익명화된 개인정보로 간주하지 않는다.

`begin()` 결과가 `Permit`일 때만 실행한다. `Replay`는 저장한 UUID·종류·버전
참조를 소유권과 현재 존재 상태를 다시 확인하여 조회한다. 없는 결과를 다시
생성하지 않는다. 같은 입력이 진행 중이면 409 `REQUEST_IN_PROGRESS`와
`Retry-After: 2`, 다른 입력이면 409 `IDEMPOTENCY_KEY_REUSED`다.
`complete(permit, reference)` 후에는 같은 참조를 재생한다. 음성처럼 재생할
결과를 보관하지 않으면 `None`으로 완료하고 재송신은 409
`REQUEST_ALREADY_COMPLETED`다. 서버 추적 ID는 이 키와 별개다.

## 원자성·수명

- 정적 Lua 소스와 분리된 인자를 사용한다. 한 Redis 서버 안에서 예약·키 등록,
  리비전 CAS·완료 기록, 삭제·모든 연결 키 제거를 각각 원자적으로 수행한다.
  Redis Cluster 다중 슬롯에서는 사용할 수 없다.
- 동시 예약 중 한 요청만 실행 권한을 얻는다. 완료에는 별도의 실행 식별자가
  필요하다. 완료 응답 유실 뒤 같은 권한·같은 결과로 재시도해도 다시 증분하지
  않는다. 다른 완료 결과는 409다.
- 같은 리비전을 가진 두 변경은 한 번만 확정된다. 패자는 409
  `VERSION_CONFLICT`로 기록하며 이후 같은 키의 재송신도 동일 오류다. 완료된
  요청 재생은 기준 리비전이 그 뒤 변경됐더라도 새 변경을 만들지 않는다.
- 일반 키의 보관은 최초 예약부터 24시간이다. 조회·완료는 TTL을 늘리지 않는다.
  임시 자원은 서버가 생성한 최대 2시간의 수명 안에서만 존재하고, 요청 키의
  TTL도 그 자원의 남은 수명 이하다. 삭제 이후의 완료는 404이며 자원을 재생성하지
  않는다. 체험의 실제 유휴 30분·활동 갱신은 #36의 수명 관리에서 연결해야 한다.
- 임시 자원당 최대 256개 예약으로 삭제 스크립트의 작업량을 제한한다. 초과하면
  429다. 이는 이 구현의 방어 상한으로 제품의 분당·일일 호출 한도(#23)를 대신하지 않는다.
- 연결 유실·프로세스 중단 뒤 실행 여부가 불확실한 예약은 자동 인계·해제하지
  않는다. 정상 보관 수명 동안 진행 상태를 유지한다. 실행 시간 초과만으로 새
  실행을 허용하면 외부 작업이 이중 수행될 수 있다. 런타임 취소 확인은 #27이다.

## 영구 저장의 별도 트랜잭션

`SaveOnce` Protocol은 영구 저장에 요구되는 경계를 명시한다. 계정·API·키의
UNIQUE 저널, 입력 해시, 기준 저장 버전 CAS, 암호화 저장본 생성, 결과 참조는
**하나의 DB 트랜잭션**에서 커밋해야 한다. Redis 완료와 DB 저장을 순차 호출하는
것만으로는 장애 시 저장 멱등성을 보장하지 못한다. DB 구현은 #75/#76에서
연결하고, 커밋 응답 유실·중복 저장 시험을 추가해야 한다. Redis가 유실되거나
24시간을 넘긴 뒤까지 외부 부작용의 정확히 한 번 실행을 보장하지 않는다.
