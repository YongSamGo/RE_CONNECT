# 백업·최신 삭제 이력·복원 체크리스트 (W12-05)

관련 #94. 선행 #90(RDS)·#25(키)·#78(삭제)과 후속 #95(복원 후 재적용)에 이어진다.
이 문서와 코드는 가상 응답(botocore Stubber)으로만 검증했다. 실제 AWS 버킷·RDS 백업·키 복구를
실행한 증거가 아니므로 운영 검증 전에는 이슈를 통과로 옮기지 않는다.

## 지키는 조건

RDS를 과거 시점으로 되돌려도 **삭제 이력은 함께 되돌아가지 않는다.** 그래서 복원한 DB에
남아 있는 삭제 대상은 서비스 공개 전에 다시 지운다.

| 저장소 | 보관 | 되돌아가는가 |
| --- | --- | --- |
| RDS 자동 백업 | 7일 (`BackupRetentionPeriod: 7`, #90 템플릿) | 시점 복구로 과거로 돌아간다 |
| RDS 수동 스냅샷 | 생성 후 29일 이내, 태그로 관리 | 생성 시점으로 돌아간다 |
| 최신 최소 삭제 이력 | 30일, 별도 S3 버킷 | 돌아가지 않는다 (덮어쓰기·삭제 불가) |
| 암호화 키 | 회전 이력 전체, RDS·S3와 다른 위치 | 돌아가지 않는다 |

복원 가능한 백업은 모두 삭제 이력 보존기간(30일) 안에 있어야 한다. 그보다 오래된 스냅샷을
복원하면 30일 전의 삭제를 다시 적용할 근거가 없어 지운 자료가 되살아난다. 이런 스냅샷은
복원하지 않고 삭제 대상으로 본다. 점검부터 `recover`까지 걸리는 시간을 고려해 하루 여유를 두고,
날짜가 아니라 시각으로 **생성 후 29일 미만**인 스냅샷만 복원 가능으로 본다.

## 삭제 이력의 위치·권한·보관기간

계획 §5 "삭제 경합·복구" 계약에 남아 있던 항목을 이렇게 정했다.

- **위치:** 전용 S3 버킷의 `deletion-events/<삭제 요청 UUID>.json`. [템플릿](../../infra/backup/deletion-journal.json)으로
  만든다. RDS 백업·EC2 볼륨·스냅샷과 독립이다.
- **내용:** `DeletionEvent`의 ID·소유자·범위·대상 UUID·동작·세대·시각뿐이다. 원문·이름·연락처는 없다.
  객체 하나는 2,048바이트를 넘지 않는다.
- **덮어쓰기 방지:** 버전 관리와 Object Lock 기본 보존 30일을 켠다. 앱은 조건부 쓰기(`If-None-Match: *`)로
  새 객체만 만들고, 이미 있으면 내용이 같을 때만 성공으로 본다.
  - 버킷 정책은 모든 주체의 보존 우회(`BypassGovernanceRetention`)·보존 변경을 거부한다.
  - 기본 모드는 GOVERNANCE다. 잘못 만든 버킷을 고치려면 관리자가 버킷 정책부터 바꿔야 하고,
    그 변경은 CloudTrail에 남는다. 더 강하게 막으려면 스택 매개변수 `LockMode`를 COMPLIANCE로 바꾼다.
- **권한:** 백엔드 EC2 역할에는 해당 접두어의 쓰기·읽기·목록과 보호 설정 조회만 준다. 삭제·수명주기·정책
  변경은 IAM에서 주지 않고 버킷 정책에서 한 번 더 거부한다. 접근 키는 쓰지 않고 인스턴스 역할로 인증한다.
  모든 호출에 버킷 소유 계정(`ExpectedBucketOwner`)을 확인한다.
- **보관기간:** 객체는 30일 동안 잠겨 있다. 수명주기가 31일째 현재 버전을 지우고 하루 뒤 이전 버전을
  정리한다. 앱의 `prune`은 S3에서 아무것도 지우지 않고 보호 설정만 확인한다. 앱은 만료된 이력을 복구에 쓰지 않는다.
- **실패 처리:** 버킷 보호 설정이 빠졌거나 쓰기·검증이 실패하면 `SERVICE_UNAVAILABLE`로 닫는다.
  외부 이력이 확정되기 전에는 실제 자료를 지우거나 삭제 성공으로 응답하지 않는다(#78 순서 그대로).

설정은 `DELETION_JOURNAL_BUCKET`·`DELETION_JOURNAL_BUCKET_OWNER`·`DELETION_JOURNAL_REGION` 셋을 함께 준다.
`APP_ENV=production`에서만 S3를 쓰고, 설정이 없으면 지금처럼 회원 저장·로그인을 열지 않는다.

## 키 복구 분리

[암호화 문서](encryption.md)의 키 규칙을 백업 관점에서 정리한다.

- 키는 RDS 스냅샷·S3 삭제 이력 버킷·소스·이미지에 넣지 않는다. 운영 키는 비밀 관리 경로에서
  실행 환경으로만 준다.
- 복구용 키 사본은 운영 계정의 RDS·S3와 다른 위치에 둔다. 보관자는 2명 이상으로 정하고, 꺼낸 기록을 남긴다.
- 7일 백업과 30일 이내 스냅샷이 참조하는 이전 키 ID는 지우지 않는다. 키 ID를 다시 쓰지 않는다.
- 복원 시험은 DB와 키를 따로 복원한 뒤 가상 표본 복호화와 변조 거절로 짝이 맞는지 확인한다.

## 수동 스냅샷 규칙

- 만들 때 `expires-at`(YYYY-MM-DD, 생성일 + 29일 이내)과 `purpose` 태그를 붙인다.
- 수동 스냅샷 내보내기·다른 리전 복사·복제본을 만들면 같은 규칙으로 따로 목록에 올린다. 만들지 않는 것이 기본이다.
- #90 템플릿의 `DeletionPolicy: Snapshot`은 스택을 지울 때 태그 없는 최종 스냅샷을 남긴다.
  만들어지면 바로 태그를 붙이거나 지운다.
- 점검은 읽기 전용 도구로 한다. 운영자 터미널에서만 실행하고 출력을 저장소·이슈에 붙이지 않는다.

```bash
python backend/manage_backups.py --db-instance <DB 식별자> --region ap-northeast-2
```

종료 코드 0은 문제 없음, 1은 발견 있음, 2는 조회 실패다. 발견 종류는 다음과 같다.

| 코드 | 뜻 | 조치 |
| --- | --- | --- |
| `automated_retention_not_7_days` | 자동 백업이 7일이 아니다 | 7일로 되돌린다 |
| `storage_not_encrypted`, `snapshot_not_encrypted` | 저장 암호화가 꺼져 있다 | 복원·공유하지 않고 원인을 확인한다 |
| `missing_expiry_or_purpose_tag` | 만료·목적 태그가 없다 | 태그를 붙이거나 지운다 |
| `expiry_beyond_deletion_history` | 만료일이 생성 후 29일을 넘는다 | 29일 이내로 줄인다 |
| `expired_delete_after_review` | 만료일이 지났다 | 확인 후 지운다 |
| `older_than_deletion_history_do_not_restore` | 생성 후 29일 이상 지났다(시각 기준) | 복원하지 않고 지운다 |

## 복원 체크리스트

재적용과 공개 전 확인은 #95(W12-06)에서 `manage_restore.py`로 묶었다. 순서는 아래로 고정한다.
격리 인스턴스는 운영 연결을 바꾸는 순간이 곧 공개다. 그래서 Nginx 점검 모드를 따로 두지 않고,
연결을 바꾸기 전에 6단계의 확인이 `ready_to_publish: true`를 내야만 진행한다.

1. **공개 차단:** 복원 DB를 운영 연결에 붙이지 않은 상태로 시작한다. 운영 DB 자체가 망가졌으면 Nginx에서 API를 닫는다.
2. **복원 지점 확인:** `manage_backups.py`로 복원할 스냅샷이 생성 후 29일 미만이고 암호화돼 있는지 본다. 자동 백업 시점 복구도 7일 이내만 쓴다.
3. **격리 복원:** 새 RDS 인스턴스로 복원한다. 보안 그룹은 복구 작업 EC2만 허용한다.
4. **키 연결:** 분리 보관한 키 버전을 복구 환경에 넣고 가상 표본 복호화·변조 거절을 확인한다.
5. **스키마 맞추기:** 스냅샷은 현재 이미지보다 옛 Alembic 버전일 수 있다. 옛 스키마에 현재 모델로 지우면
   일부 표를 놓칠 수 있으므로 재적용보다 먼저 올린다. `migrate.env`·`app.env`의 DB 주소를 복원 인스턴스로 바꾼 뒤:
   1. `docker compose --env-file /run/reconnect/images.env -f infra/compose.prod.yaml run --rm migrate`
   2. 같은 migrator 계정으로 `infra/aws/grant_runtime.sql`을 다시 실행한다. 복원 DB의 역할·암호는 스냅샷 시점 값이다.
6. **삭제 재적용과 공개 전 확인:** 같은 S3 버킷을 그대로 둔 채 실행한다.

   ```bash
   docker compose --env-file /run/reconnect/images.env -f infra/compose.prod.yaml --profile restore run --rm restore-check
   ```

   한 번에 다음을 한다. 출력은 건수와 판정뿐이고 회원 ID·대상 ID·본문은 없다.
   - Alembic head가 아니면 재적용하지 않고 `schema_not_current`로 닫는다 (5단계로 돌아간다).
   - 버킷 보호 설정(버전 관리·Object Lock 30일 이상)을 확인한다.
   - 30일 안의 최신 삭제 이력을 모두 재적용한다(`recover`). 같은 이력을 다시 적용해도 결과가 같다.
   - 스냅샷 시점에 진행 중이던 삭제(대기·실패)를 끝낸다(`retry`).
   - 이력마다 다시 확인한다: 삭제 기록이 완료인지, 대상(계정·프로필 전 버전·지원서·초안·응답 기록·철회한 동의)이
     남지 않았는지, 회원 세션 세대가 이력 세대 이상인지. 대기·실패가 0인지.

   종료 코드 0(`ready_to_publish: true`)만 다음 단계로 간다. 1은 문제 건수가 있음, 2는 조회 실패다.
   쓴 지 30일이 지난 객체는 수명주기가 아직 지우지 않았어도 읽지 않고 한도에서 뺀다.
   유효한 이력이 1,000건을 넘거나 목록이 10,000개를 넘으면 2로 닫힌다. 이때는 공개 차단을 유지하고,
   한도를 올리는 코드 변경을 리뷰받아 배포한 뒤 다시 실행한다. 일부만 재적용한 채 공개하지 않는다.

   | 문제 코드 | 뜻 |
   | --- | --- |
   | `schema_not_current` | 복원 DB가 현재 이미지의 Alembic head가 아니다 |
   | `record_missing` · `record_mismatch` · `record_not_completed` | 이력에 맞는 삭제 기록이 없거나 다르거나 끝나지 않았다 |
   | `target_remains` | 삭제 대상이 복원 DB에 남아 있다 |
   | `session_not_revoked` | 회원 세션 세대가 이력보다 낮다(이전 세션이 살아날 수 있다) |
   | `deletions_waiting` | 대기·실패 상태 삭제가 남았다 |

7. **다시 확인:** 운영 연결을 바꾸기 직전에 `restore-check --verify-only`로 읽기만 하는 확인을 한 번 더 한다.
   증거에는 건수와 성공 여부만 `security-reports/`에 남기고, 커밋하는 진행 기록에는 판정만 옮긴다.
8. **공개:** 운영 연결을 바꾸고 API를 연다. 쓰지 않는 복원 인스턴스와 임시 스냅샷은 지운다.

로컬 리허설(실제 `pg_dump` 스냅숏 → 별도 DB 복원 → 옛 스키마 거절 → migrate → 재적용·확인)은
`backend/tests/test_restore_rehearsal.py`로 재현한다. 잠금을 지원하는 S3 에뮬레이터가 있을 때만 실행되고
CI에서는 건너뛴다. 실행 방법과 결과는 [W12-06 리허설 기록](../progress/w12-06-restore-rehearsal.md)에 있다.
