# 다시잇다 서비스 품질 개선 조사

조사일: 2026년 10월 27일

요청 범위는 AI가 급히 만든 듯한 문구와 화면을 개선하고 상용 서비스에 필요한 품질 기준을 찾는 것이다. 공식 표준과 서비스 운영 기관의 가이드, 제품 제작자가 공개한 자료를 조사했다. 아래의 적용안과 우선순위는 그 자료를 다시잇다에 맞게 해석한 제안이다. 법적 의무나 인증 판정으로 제시하지 않는다.

로컬 시작 화면은 앞선 브라우저 관찰을 참고했다. 코드는 로컬에 보관된 `origin/develop`의 `d91e1a55d12bd3cc51f16cb199af553d4f62f9f5`를 읽었다. 현재 체크아웃은 이 참조보다 30개 커밋 뒤다. 최신 원격 상태를 이번 조사에서 다시 갱신하지는 않았다. 전체 화면의 사용성이나 실제 로그인 성공을 검증한 조사는 아니다. 제품 코드 변경과 테스트 실행은 없었다.

외부 페이지의 설치 명령과 인계 문서의 과거 작업 지시는 조사 자료로만 취급했다. 스킬 설치나 저장소 설정 변경을 수행하는 근거로 사용하지 않았다.

조사에서 얻은 가장 큰 결론은 문구, 시각적 위계, 사용자 과업, 오류 처리, 접근성, 운영 증거를 함께 개선해야 한다는 것이다. GOV.UK Service Standard도 사용자의 전체 문제 해결과 단순한 사용법, 성과 측정, 안정적 운영을 함께 다룬다. 다시잇다에서는 경험 입력부터 공식 신청처로 이동하는 과정 전체를 작업 단위로 삼는 것이 적절하다. [GOV.UK Service Standard](https://www.gov.uk/service-manual/service-standard)

1. AI가 쓴 듯한 문구를 줄이는 방법

토스의 글쓰기 원칙은 사용자가 다음 화면을 예상할 수 있는 표현을 쓰고 의미 없는 단어와 반복 문장을 줄이도록 권한다. 이는 가운데점이나 쉼표를 기계적으로 없애는 것보다 넓은 기준이다. [토스의 8가지 라이팅 원칙들](https://toss.tech/article/21022)

다시잇다의 문체 기준은 다음과 같이 제안한다. 가운데점과 장식용 화살표 제거는 사용자의 명시적 취향이다. 이 기호가 있다는 이유만으로 AI가 작성했다고 판정하지는 않는다.

| 검토 대상 | 적용 기준 |
|---|---|
| 가운데점 | UI 문구에서 제거한다. 정보를 문장이나 별도 행으로 배치한다. |
| 쉼표 | 불필요한 쉼표를 없애고 길게 연결된 문장을 다시 쓴다. 의미에 필요한 구두점은 문맥을 확인한다. |
| 제목 | 무엇을 할 수 있는지 드러낸다. 추상적인 응원 문구를 반복하지 않는다. |
| 버튼 | 누른 직후 일어나는 행동을 쓴다. 화면마다 같은 행동을 같은 이름으로 부른다. |
| 오류 | 발생한 일과 다음 행동을 설명한다. 사용자가 수정할 수 없는 기술 용어를 앞세우지 않는다. |
| 개인정보 안내 | 처리 목적과 보관 여부를 사실대로 쓴다. 문장을 줄이면서 조건을 삭제하지 않는다. |
| 말투 | 성인 사용자를 존중하는 해요체를 기본으로 한다. 과한 칭찬이나 어린아이를 대하는 표현을 피한다. |
| 예시 | 가상 예시임을 표시한다. 이용자 수나 후기, 추천 정확도를 지어내지 않는다. |

아래는 방향을 설명하는 문구 제안이다. 실제 화면의 기능과 서버 응답에 맞춰 확정해야 한다.

| 현재 표현 또는 검토 대상 | 수정 제안 | 확인할 점 |
|---|---|---|
| 당신의 경험에 새로운 쓰임을 잇다. | 해온 일을 정리하고 일자리와 봉사 기회를 찾아보세요. | 실제 서비스 범위를 설명하는지 확인 |
| 내 속도에 맞춰, 한 걸음씩. | 순서 안내와 중복되면 문구 삭제 | 삭제해도 정보가 사라지지 않는지 확인 |
| 결정은 내가 직접 | 정리된 내용을 직접 고칠 수 있어요 | 해당 화면에 실제 수정 기능이 있어야 함 |
| 시작 화면으로 → | 시작 화면으로 | 장식용 문자 제거 |
| UX01 또는 단계 코드 | 내부 식별자는 개발 문서에 두고 사용자에게는 화면 목적을 표시 | 진행 단계가 실제로 필요한지는 따로 판단 |
| 저장 오류 안내 | 저장하지 못했어요. 다시 시도해 주세요. | 입력 보존 여부를 확인한 뒤 보존 안내를 추가 |

사용자에게 보이는 문자열을 화면, 상태, 현재 문구, 수정 문구, 변경 이유, 기능 조건으로 기록한다. 제목과 본문에 같은 설명이 반복되는지도 함께 본다. 구두점을 정규식으로 일괄 삭제하면 날짜, 금액, 코드, 약관의 뜻이 바뀔 수 있으므로 문장 단위로 검토한다.

2. 시각적 완성도를 높이는 방법

UI Craft는 반복적인 카드 배열, 장식적인 그라데이션, 의미 없는 움직임 등 흔한 패턴을 점검할 수 있는 참고 자료다. 이 규칙은 특정 제작자의 디자인 관점이다. 모든 카드나 그라데이션이 나쁜 디자인이라는 보편적 표준으로 쓰지는 않는다. [UI Craft의 패턴 예시](https://skills.smoothui.dev/anti-slop)

현재 로컬 홈에서는 안내 문장과 큰 제목, 설명, 주요 버튼, 순서 안내 패널이 보인다. 초록색 계열의 본문과 연한 배경을 광범위하게 사용하며 문자 기호를 로고와 장식에 사용한다. 기본 본문 크기와 키보드 초점 표시 등은 기존 코드에 이미 있으므로 활용한다. 전체 화면이 같은 문제를 가진다고 단정하지 않는다.

첫 화면은 사용자가 무엇을 얻는지 구체적으로 보여주는 쪽으로 다듬는다. 오른쪽 순서 안내 패널에 더 많은 장식을 추가하기보다 짧은 입력 예시와 정리 결과를 보여주는 제품 미리보기를 검토한다. 예를 들어 가상 입력인 ‘도서관에서 책을 정리하고 방문자를 안내했어요’를 ‘자료 정리’와 ‘이용자 안내’로 정리하는 모습을 보여줄 수 있다. 예시에서 말하지 않은 경력이나 자격을 추가하지 않는다.

이전 제안의 색상은 초안으로 유지하되 실제 화면의 대비와 사용자 반응을 확인한 뒤 확정한다. 바탕 `#F5F8F4`, 표면 `#FFFFFF`, 글자 `#182820`, 주요색 `#25634B`, 작은 강조 `#DDEBA7`, 경계선 `#D6DFD7`이다. 작은 강조색은 본문 글자색으로 사용하지 않는다. 서체는 한글 산세리프 한 종류를 기본으로 검토하고 본문 18px 이상, 주요 버튼 높이 48~56px를 프로젝트 목표로 삼는다. 이 수치는 WCAG가 요구하는 일률적인 최소 글자 크기가 아니다.

시각 규칙은 다음 순서로 정한다.

- 제목, 본문, 보조 설명의 크기와 굵기
- 콘텐츠 폭과 모바일 여백
- 주요 버튼과 보조 행동의 위계
- 카드가 필요한 정보와 열린 목록으로 충분한 정보
- 입력창과 선택 항목의 상태
- 아이콘의 의미와 선 두께
- 입력이나 선택에 응답하는 짧은 움직임

글자 크기, 간격, 색상, 모서리, 초점 표시를 공통 값으로 관리한다. 새로운 UI 라이브러리를 넣기 전에 기존 Button, Fields, StatusNotice와 API 요청 처리 구조를 기준으로 확장할 수 있는지 확인한다. 이는 재구현과 스타일 중복을 줄이기 위한 프로젝트 적용안이다.

3. 실제로 끝까지 사용할 수 있게 만드는 방법

GOV.UK의 질문 화면 패턴은 꼭 필요한 정보만 묻고 한 화면에 한 질문부터 시작하며 뒤로 이동할 때 이전 상태를 유지하도록 권한다. 진행 표시도 사용자에게 도움이 되는지 확인한 뒤 추가한다. [GOV.UK 질문 화면 패턴](https://design-system.service.gov.uk/patterns/question-pages/)

다시잇다는 채팅의 외형보다 한 번에 답할 수 있는 질문과 수정 가능한 결과가 중요하다. 이미 대화형 입력과 프로필 확인 경로가 있으므로 이를 중심으로 경험을 설계한다. 질문이 동적으로 달라져 전체 개수를 모를 때 ‘3/5 단계’처럼 정확하지 않은 진행률을 표시하지 않는다.

| 화면 | 우선 개선할 행동 | 완료 판단에 필요한 증거 |
|---|---|---|
| 시작과 처리 안내 | 비회원 시작과 공고 탐색을 구분하고 실제 체험으로 진입 | 주요 버튼에서 실제 동의와 체험 생성으로 이어짐 |
| 경험 입력 | 한 질문에 답하고 필요하면 음성 대신 글로 입력 | 제출 결과가 표시되고 실패 원인에 맞게 재시도 가능 |
| 프로필 확인 | AI가 정리한 사실을 고치고 확정 | 수정 내용과 확정 상태가 서버 결과와 일치 |
| 공고 목록과 상세 | 지역과 활동 조건, 모집 기간을 비교 | 현재 공개 가능한 공고만 표시하고 공식 출처를 확인 가능 |
| 신청 준비 | 준비물과 공식 신청 경로를 이해 | 실제 신청 여부를 사이트 내부 저장과 혼동하지 않음 |
| 로그인과 저장 | 카카오 인증 후 원래 작업으로 돌아와 저장 | 인증과 저장을 별도 상태로 표시하고 결과를 확인 |
| 내 자료 | 저장본을 다시 찾고 수정하거나 삭제 | 해당 계정의 실제 서버 결과와 화면 상태가 일치 |

기존 소스에는 미리보기 경로와 서버 연동 경로가 함께 있다. 이는 코드 정적 확인 사항이다. 홈의 미리보기 동의 경로를 운영 서비스처럼 보이게 꾸미는 것만으로 실제 여정이 완성되지는 않는다. 운영 진입과 정책이 준비되면 의도한 경로로 연결해야 한다. 개발 상태 고지는 현재 기능 상태에 맞춰 유지하고 실제 배포 준비가 끝난 뒤 노출 범위를 정한다.

4. 오류와 기다림을 제품의 일부로 설계하는 방법

KRDS는 어떤 문제가 어디서 생겼는지와 고칠 방법을 설명하고 오류 이후에도 사용자 입력값을 유지하도록 안내한다. [KRDS 오류 패턴](https://www.krds.go.kr/html/site/global/global_07.html)

화면마다 초기, 처리 중, 성공, 빈 결과, 실패, 만료, 권한 부족 상태가 필요한지 검토한다. 모든 화면에 일곱 상태를 억지로 만들지는 않는다. 실제 API 계약과 사용자 행동에 해당하는 상태만 만든다.

| 발생 상황 | 화면이 해야 할 일 |
|---|---|
| 처음 목록을 읽음 | 어떤 정보를 불러오는지 알리고 결과 영역이 갑자기 크게 움직이지 않게 함 |
| 메시지나 저장 요청 중 | 중복 제출을 막고 실제 처리 상태를 표시 |
| 응답이 느림 | 작업 목적에 맞는 안내 제공. 근거 없는 남은 시간이나 가짜 진행률 금지 |
| 결과 없음 | 현재 조건을 보여주고 조건을 바꾸는 행동 제공 |
| 로그인 취소 | 인증 취소 사실을 알리고 원래 작업으로 돌아갈 수 있게 함 |
| 세션 만료 | 다시 인증해야 하는 이유와 남아 있는 자료의 범위를 설명 |
| 저장 결과 불명 | 서버에서 저장됐는지 확인하기 전 완료라고 표시하지 않음 |
| 입력 오류 | 해당 필드 근처에 원인을 설명하고 초점과 오류 요약을 연결 |
| 서비스 장애 | 재시도와 문의 경로를 제시하고 반복 입력을 줄임 |

‘입력이 남아 있어요’는 실제 보존 범위가 확인된 경우만 쓴다. 개인정보를 브라우저에 영구 저장해서 해결할지는 보관 정책과 함께 결정한다. 화면 요청을 중지하는 기능이 서버 처리를 취소하지 못한다면 두 동작을 같은 뜻으로 표시하지 않는다.

5. AI 기능의 신뢰를 설계하는 방법

Google PAIR는 사용자가 AI를 적절한 수준으로 신뢰하도록 능력과 한계, 결과에 영향을 준 정보, 수정과 통제 방법을 설명하도록 권한다. 자동화가 실패했을 때 사용자가 계속할 수 있는 경로도 필요하다. [PAIR Explainability + Trust](https://pair.withgoogle.com/guidebook-v2/chapter/explainability-trust/) [PAIR Feedback + Control](https://pair.withgoogle.com/guidebook-v2/chapter/feedback-controls/)

다시잇다에서는 AI가 정리한 내용을 초안으로 표시하고 직접 수정하는 행동을 눈에 띄게 배치한다. 추천 이유는 입력한 경험과 실제 공고 조건에서 확인 가능한 사실로 설명한다. 확인되지 않은 자격은 미확인으로 표시하고 공식 공고에서 확인하게 한다. 내부 추천 점수를 ‘합격 가능성 92%’ 같은 숫자로 표현하지 않는다. 저장 동의와 로그인, 내용 확정은 서로 다른 일이므로 상태와 문구도 구분한다.

AI가 만든 경험 요약의 품질도 디자인 범위에 넣는다. 같은 입력에서 결과가 지나치게 부풀려지거나 실제로 말하지 않은 경력이 추가되면 매끄러운 화면이 오히려 잘못된 신뢰를 만들 수 있다. 예시 입력별로 사실 보존, 쉬운 말, 편집 가능성, 빈 정보 처리 기준을 정하고 모델 변경 때 결과를 비교할 계획을 세운다. 이번 조사에서 모델 평가를 실행한 것은 아니다.

6. 고령 사용자와 모바일 환경에서 확인하는 방법

W3C는 고령 사용자의 시력, 작은 조작 표적, 집중과 기억의 부담을 기존 접근성 기준으로 다룰 수 있다고 설명한다. 나이만으로 사용 능력을 가정하기보다 실제 사용자를 포함해 확인하는 접근이 필요하다. [W3C 고령 사용자 접근성](https://www.w3.org/WAI/older-users/)

| 항목 | 근거 또는 기준 | 다시잇다 적용안 |
|---|---|---|
| 일반 텍스트 대비 | WCAG AA는 보통 4.5:1, 큰 글자는 3:1 | 설명과 오류, 비활성 상태의 의미를 색 외 방법으로도 전달 |
| 글자 확대 | 200% 확대 시 내용과 기능 손실 방지 | 긴 한글 제목, 동의문, 버튼, 고정 영역을 함께 확인 |
| 조작 표적 | WCAG 2.2 AA의 SC 2.5.8은 24×24 CSS px 또는 규정된 예외와 간격 | 주요 조작은 48~56px 높이로 더 넉넉하게 설계 |
| 키보드 | 주요 작업을 키보드로 수행하고 초점을 볼 수 있어야 함 | 모달 종료와 오류 후 이동, 화면 전환 후 초점 확인 |
| 입력 방식 | 한 방식이 막혀도 필요한 일을 수행할 수 있는지 검토 | 음성 권한을 거절한 뒤에도 글로 경험 입력 가능 |

위 표의 일부 항목만으로 WCAG 전체 적합성을 판정하지 않는다. 자동 접근성 도구의 위반 0건도 실제 스크린리더 사용성과 동일하지 않다. 저장소의 ACCESSIBILITY.md 역시 기존 자동 검사와 실제 기기 검증의 범위를 구분해 기록하고 있다.

[W3C 대비 설명](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) [W3C 글자 확대 설명](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html) [W3C 최소 표적 설명](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) [WCAG 2.2 표준](https://www.w3.org/TR/WCAG22/)

7. 성능과 운영 준비를 연결하는 방법

Google의 Core Web Vitals 권장값은 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하이며 모바일과 데스크톱을 나눠 실제 방문의 75백분위수로 평가한다. [Web Vitals](https://web.dev/articles/vitals)

다시잇다에서는 이 값을 배포 후 성능 목표로 삼는다. LCP는 주요 콘텐츠가 보이는 속도, INP는 입력과 클릭에 화면이 응답하는 속도, CLS는 화면이 예기치 않게 움직이는 정도다. INP 200ms가 AI 응답을 200ms 안에 생성해야 한다는 뜻은 아니다. 모델 처리 시간은 별도로 측정하고 처리 중 피드백과 장애 안내를 설계해야 한다.

초기에는 방문 데이터가 부족할 수 있으므로 대표 모바일과 제한된 네트워크에서 개발 측정을 진행한다. 배포 후 데이터가 쌓이면 실제 사용 지표와 비교한다. Lighthouse 한 번의 점수를 실제 이용자 성능으로 간주하지 않는다.

도메인과 HTTPS, 운영 로그인, DB 보관과 삭제, 백업과 복원, 장애 알림, 문의 수단은 공개 운영 판단에 필요한 별도 준비다. 앞선 저장소 조사에서 운영 증거가 부족했던 부분은 팀의 실제 AWS 상태와 연결해 확인해야 한다. 본 문서는 AWS 콘솔이나 운영 자원을 조사한 결과가 아니다.

8. 도구 도입을 판단하는 방법

UI Craft에서 우선 가져올 것은 제품 이해, 공통 토큰, 화면별 상태 검토, 렌더링 결과 비평이라는 절차다. 도구 문서는 점수가 정적 패턴, 토큰 규칙, 일부 접근성 검사로 구성되고 React와 Tailwind 형태에 더 잘 맞으며 일반 CSS에서는 약하다고 설명한다. 다시잇다는 일반 CSS를 사용하므로 자동 점수로 전체 완료를 결정하기 전에 실제 탐지 범위를 확인해야 한다. [UI Craft 점수 문서](https://skills.smoothui.dev/docs/score)

제작자의 별도 실험 글도 시각적 비율과 색 면적, 컨테이너 밀도를 합친 수치가 품질 순위를 제대로 설명하지 못했다고 밝힌다. 이 글은 해당 시각 측정 실험의 한계에 대한 설명이며 기존 정적 검사 점수 전체가 폐기됐다는 뜻으로 읽지 않는다. [UI Craft 측정 실험의 한계](https://skills.smoothui.dev/blog/commitment-metric-measuring-presence)

따라서 점검 도구는 실수와 퇴행을 찾는 보조 수단으로 활용한다. 사용자가 서비스를 이해하고 실제 작업을 마칠 수 있는지는 렌더링된 화면과 과업 관찰로 확인한다.

9. 다시잇다의 실행 우선순위

아래 우선순위는 이번 조사에서 제안하는 작업 순서다. 저장소 코드 리뷰 심각도 P1~P4와는 다른 분류다. 개인별 담당자는 팀에서 확정하되 역할 단위로 정리했다.

| 순서 | 작업 | 주 담당 역할 | 산출물과 완료 기준 |
|---|---|---|---|
| 1 | 최신 소스와 실행 상태 정리 | 프론트엔드와 백엔드 | 기준 커밋, 실제 실행 위치, 미리보기와 서버 경로, 연동 상태 기록 |
| 2 | 핵심 사용자 과업과 상태 정의 | 기획과 전체 팀 | 경험 입력부터 공식 신청처 이동까지 단계별 성공과 실패 조건 |
| 3 | 문구 전수 목록과 공통 디자인 값 | 프론트엔드와 기획 | 문구 작업표, 색상과 글자 체계, 입력과 버튼의 상태별 규칙 |
| 4 | 시작 화면과 동의 화면 개선 | 프론트엔드 | 모바일과 PC 시안, 예시 표시, 실제 시작 경로와 일치하는 버튼 |
| 5 | 경험 입력부터 신청 준비까지 개선 | 프론트엔드와 백엔드 | 서버 결과와 일치하는 수정, 확정, 추천 이유와 공식 안내 |
| 6 | 카카오 로그인과 저장 복귀 완성 | 프론트엔드와 백엔드 | 성공과 취소, 인증 만료, 저장 여부 확인, 재로그인 후 조회 |
| 7 | 오류 복구와 접근성 점검 | 전체 팀 | 입력과 저장 상태의 정확한 안내, 실제 기기와 키보드 확인 |
| 8 | 목표 사용자 관찰과 수정 | 기획과 전체 팀 | 과업별 막힘 기록, 수정 결과, 남은 출시 제약 |
| 9 | 배포 성능과 운영 증거 확인 | 인프라와 백엔드 | 성능 기준선, 장애 대응과 복원 기록, 운영 연락 수단 |

각 화면은 문구, 배치, 정상 상태, 실패 상태를 묶어 개선한다. 글 전체를 먼저 갈아엎은 뒤 기능을 연결하는 방식은 실제 상태와 어긋나는 문구를 만들 수 있으므로 핵심 과업 단위로 끝낸다. 예상 일정은 최신 코드와 팀 병행 작업을 확인한 뒤 산정한다.

10. 완료를 확인하는 방법

GOV.UK의 진행자 동반 사용성 관찰은 실제 또는 예상 사용자가 구체적인 과업을 수행하는 모습을 보도록 권한다. 과업 설명에 버튼 이름이나 정답 경로를 넣지 않는 것이 중요하다. [GOV.UK 사용성 관찰 방법](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing)

첫 관찰은 스마트폰 숙련도가 다른 목표 사용자 5~6명으로 시작하는 방안을 제안한다. 이는 이번 프로젝트의 질적 관찰 계획이며 모든 문제를 발견하거나 통계적 대표성을 확보하는 인원 기준이 아니다. 관찰 뒤 수정하고 다시 확인한다.

- 가입 없이 자신의 경험을 한 가지 입력한다.
- 잘못 정리된 경험을 수정하고 확인한다.
- 자신의 지역과 조건에 맞는 공고를 찾는다.
- 카카오 로그인을 취소했다가 다시 시도한다.
- 자료를 저장한 뒤 다시 로그인해서 찾는다.
- 신청 준비를 마치고 어디에서 실제 신청하는지 설명한다.

기록할 항목은 혼자 완료했는지, 어디서 멈췄는지, 입력이 사라졌는지, 재시도할 수 있었는지, 현재 자료가 저장됐다고 이해하는지다. ‘디자인이 예쁜가요’라는 질문만으로 판정하지 않는다.

공개 운영 전에는 핵심 경로의 진행 불가, 자료 보존 상태의 잘못된 안내, 로그인과 저장의 결과 불일치를 해결한다. 성능과 접근성은 위 기준으로 별도 확인한다. 시각 평가는 제목과 행동의 위계, 읽기 편한 문구, 의미 있는 아이콘, 화면 간 일관성, 모바일 배치를 실제 화면에서 검토한다. AI 티 제거율이나 임의의 미감 점수를 출시 근거로 만들지 않는다.

이번 조사로 앞선 디자인 계획에 추가할 항목은 실제 제품 예시를 보여주는 홈 구성, 상태별 문구 작업표, 로그인 후 작업 복귀, 입력과 저장 결과의 정확한 안내, 목표 사용자 관찰, 배포 후 성능 측정이다. 문구와 디자인 개선은 기존 API 계약과 개인정보 처리 조건을 함께 확인하며 진행한다.
