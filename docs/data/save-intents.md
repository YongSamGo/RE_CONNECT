# 승인 자료의 일회 저장 전달 — W10-03

## 발급

`POST /api/v1/auth/save-intents`는 익명 세션의 현재 체험 ID, 확정 프로필 버전, 선택한 승인 지원서 ID/리비전만 받는다. 프로필이 필수이며 지원서만 숨겨서 담지 않는다. 클라이언트가 본문·소유자·승인 시각을 지정할 수 없다. 회원 세션은 `ALREADY_SIGNED_IN`이다.

Origin·서명 CSRF·HTTP 한도·UUID 멱등 키를 검사한다. 실제 Redis Lua 하나가 세션/체험 수명과 소유권, 현재 확정 프로필, 지원서 리비전/승인을 검사하고 서버 승인본만 복사한다. 전체 대화·음성·미확정 초안은 복사하지 않는다. 대기 내용은 최대96KiB이며 Redis 비영속 설정을 사용한다.

세션당 대기는 하나이고 새 발급은 이전 대기를 폐기한다. 같은 키/입력은 같은 살아 있는 대기를 반환하고 TTL을 연장하지 않는다. 같은 키/다른 입력은 충돌이고, 이미 교체·만료된 키로 이전 내용을 되살리지 않는다. 세션당 새 발급은 최대32회이며 한도 응답에 Retry-After가 있다.

만료는 발급 후10분과 원래 세션의 남은 수명 중 짧은 값이다. 조회·재전송·로그인은 원래 만료 시각을 연장하지 않는다. 대기 ID·본문을 URL로 전달하지 않는다.

## 인증 왕복과 정리

`GET /auth/kakao/start?purpose=save`는 현재 살아 있는 대기가 있을 때만 시작한다. OAuth state의 서버 기록에 해당 대기 ID를 함께 묶는다. 왕복 중 새 대기가 발급되면 이전 state로 새 대기를 옮길 수 없다. 취소·실패는 해당 state의 대기만 폐기하며 이후 새 대기를 지우지 않는다. 만료·교체는 expired다.

검증한 제공자 신원으로 내부 계정을 확인한 뒤 단일 Redis Lua로 새 회원 세션/주체/CSRF를 만들고 정확한 대기만 새 회원/세션에 결합한다. 동시에 이전 세션·OAuth state와 그 세션의 체험 본문·지원서·확정본·요청 결과를 삭제한다. 체험 생성 시 서버 자원 인덱스를 남기며 세션당 최대60개, 자원당 최대256개 요청을 삭제 전 검사한다. 늦게 끝난 추론은 기존 세션/자원 검사를 통과하지 못한다.

일반 login은 대기를 이전하지 않는다. logout은 대기/체험 정리와 이전 인증 회수를 먼저 원자 처리한 뒤 후속 정리를 기다린다. 별도 내부 revoke도 대기를 지운다. Redis 장애·정리 인덱스 이상은 성공으로 바꾸지 않는다.

## 동의·교체 확인·일회 소비

로그인 성공은 자료 저장이 아니다. `GET /me`가 대기의 ID/원래 만료/대상 여부와 현재 회원의 저장 프로필 버전만 반환한다. 본문은 응답하지 않는다. 익명 AI 동의는 회원 저장 동의로 상속하지 않는다. `POST /consents`는 실제 회원 세션을 검증한 내부 User로 목적별 SQL 동의를 기록하고 me는 현재 버전의 동의만 반환한다.

`SaveIntentService.consume`은 #75/#76 저장 서비스가 호출할 내부 경계다. 현재 회원과 실제 저장 안내문 버전, 최신 미철회 저장 동의, 명시적인 base_saved_version을 확인한다. 기존 저장본이 없으면 기준은 null이다. 기존 버전이 있는데 기준을 생략하거나 다른 버전을 주면 소비 전에 충돌한다. User 행 잠금 안에서 검사하고 Redis가 같은 회원/세션/대기를 한 번만 반환·삭제한다.

호출자는 전달받은 SQL 트랜잭션과 승인 스냅샷으로 실제 저장을 구현해야 한다. writer 종료 뒤 세션을 다시 검사하며 오류·취소·로그아웃이면 SQL 작업을 롤백한다. 회원 세션 전환은 Redis 인증을 회수한 뒤 같은 PostgreSQL User 행 잠금 경계를 지나서 성공을 반환한다. 기존 writer가 있으면 최종 세션 검사로 롤백되거나 전환 성공 이전에 끝난다. 잠금 제한1초를 넘기면 이전 인증은 회수한 상태로503이며 성공을 가장하지 않는다. SQL 오류가 나도 이미 소비한 대기를 부활시키지 않는다. 분산 트랜잭션은 없으므로 이 경우 다시 확인/발급해야 한다. 저장 성공 후 HTTP 재시도의 멱등성은 #75/#76의 SQL 저장 기록으로 구현해야 한다.

이 이슈는 영구 저장/암호화·조회 API를 대신하지 않는다. #75/#76은 승인본 암호화, 현재 공고·근거 재검토, 소유권, 결합 저장 및 멱등 기록을 writer 안에 연결해야 한다. 현재 consume은 HTTP에 직접 노출하지 않는다. 로그인만으로 ProfileVersion/ApplicationDraft를 생성하지 않는다.

## 검증과 운영 조건

실제 Redis·SQLite/PostgreSQL·ASGI에서 발급/재전송/교체/소유권/CSRF, 정확한 state 결합, 취소/만료, 새 세션 이전과 기존 체험 삭제·늦은 결과 차단, 저장 동의·교체 기준, 경합 소비, SQL 실패·취소·로그아웃 롤백을 시험한다. 실제 loopback TCP API에서도 프로필 확정→발급→가상 제공자 왕복→회원 동의→logout을 확인한다.

시험의 제공자와 안내문은 명시적 가상 대역이다. 운영 주체·문의처·AWS 리전·보관/삭제 정책은 미정이므로 실제 AI_NOTICE_VERSION/STORAGE_NOTICE_VERSION을 설정하지 않는다. 실제 카카오 정상 승인·운영 HTTPS·EC2·기기 및 #75/#76 저장 API는 별도 검증이 필요하다.

## 프로필 저장 소비자 연결

#75 [프로필 암호화 저장](saved-profiles.md)이 같은 SQL 잠금/트랜잭션과 응답 기록을 사용해 프로필 단독 대기를 실제로 소비한다. 지원서 포함 대기는 명시적 프로필 저장을 먼저 수행하고, 원래 만료 그대로 대기를 보존해 #76 지원서 저장 단계에서 이어 소비한다. 프로필 부분의 다른 키 재사용은 SQL 고유 기록으로 거절한다.
