# 수집 중복과 불변 버전 (W06-04)

`app.state.opportunity_ingestion_service.record(RecordOpportunity)`에 정규화한
`OpportunitySnapshot`을 전달한다. Snapshot은 공통 `OpportunityContent`와
`description_truncated`만 받는다. 출처·외부 ID·확인 시각·수동 대조 대상은 서버의
수집/운영 서비스가 정한다. 검수 상태·공개 포인터·해시는 입력으로 받지 않는다.
외부 HTTP나 원문 해석은 이 트랜잭션 전에 끝내야 한다(#45/#46/#49).

## 생성·재전송·변경

- PostgreSQL의 짧은 트랜잭션에서 Source → OpportunityDocument 순서로 행을
  잠근다. 기존 `(source_id, external_id)` UNIQUE와 같은 출처 잠금으로 동시
  최초 생성·버전 증가·ID 없는 수동 대조를 직렬화한다. 운영자 수정도 같은 잠금
  순서를 사용해야 한다(#53/#54). 네트워크·모델 작업 중에는 잠금을 잡지 않는다.
- 신규 문서는 버전 1 pending, 본문 변경은 직전 버전+1 pending이다. 공개 포인터와
  검수 시각은 변경하지 않는다. DB 불변 트리거를 유지하며 본문 UPDATE를 하지 않는다.
- 같은 정규화 본문은 새 버전 없이 관측한 버전의 source_checked_at만 갱신한다.
  새 pending 본문을 다시 보았다고 옛 공개본의 확인 시각까지 늘리지 않는다.
- 과거 확인 시각의 늦은 결과는 stale로 무시한다. 동일 시각에 다른 내용은 409다.
  수집 시각은 외부 원문 문자열이 아닌 서버 관측 시각이다. 미래 관측은 거절한다.
- 원자 커밋 응답이 유실되면 같은 출처/외부 ID/관측으로 재시도해 기존 ID와 버전을
  찾는다. 실패한 트랜잭션은 문서와 버전을 함께 롤백하고 고정 503만 반환한다.
- source.last_success_at·실행 집계, 출처 enabled/승인 설정·공식 URL 확인은 수집
  실행 서비스(#44/#45/#49)가 검사한다. 이 저장 경계가 수집 권한/출처 신뢰를 부여하지 않는다.

해시는 정규화한 생성 시점 Snapshot의 JSON을 키 순서에 무관하게 SHA-256으로
계산한다. 배열 순서는 보존한다. 해시는 공개 승인·원문 진위의 증명이 아니다.
모집 종료 projection은 기존 버전에 바로 반영할 수 있으므로 생성 해시와 현재
상태만 비교해 동일성을 결정하지 않는다. 실제 계약 필드도 비교하여 닫힌 공고의
재개를 놓치지 않는다. 해시/본문을 예외나 로그에 출력하지 않는다.

## 중요 변경과 종료

`versions.py`의 `IMPORTANT_FIELDS`, `IMPORTANT_STATUS_TRANSITIONS`,
`important_changes()`가 Plan/02 §6의 공통 규칙이다. 공개 조회도 같은 필드 목록으로
공개본보다 새 pending 버전의 중요 변경을 SQL에서 확인한다.

| 처리 | 변경 |
| --- | --- |
| 재검수 전 추천·지원서 보류 | 활동 유형, 조건, 지역, 원격, 일정·시간, 마감, 접수 방식·URL·안내, 서류, 유급 여부, 원문 URL |
| 상태 변경으로 보류 | closed→open, open→unknown |
| 새 pending이나 중요 변경 보류 아님 | 제목·설명·역할/역량 등 위 목록 밖의 필드 |
| 즉시 닫기 | 원문 모집 종료·현재 마감 경과 |

종료만 변하면 기존 상태를 닫고 새 본문 버전을 만들지 않는다. 종료와 본문 변경이
함께 오면 본문은 새 pending이고 현재 공개본과 최신 관측 버전의 상태는 즉시 닫는다.
재개는 pending 새 버전으로만 들어가며 승인 전 공개본을 열지 않는다.
이전의 중요 pending이 여러 개 남으면 해결 전까지 보수적으로 보류한다. 자동 반려나
과거 검수 이력을 덮어쓰는 경로는 추가하지 않는다. 실제 추천·지원서 서비스는
공유 규칙과 현재 공개본을 함께 검사해야 한다(#63/#67).

## ID 없는 수동 자료

같은 출처에서 공식 URL·기관·제목·마감 날짜/시각이 겹치는 문서를 대조한다.
동일 후보가 있으면 409로 멈추고 운영자가 기존 문서/모집기간을 확인한 뒤
`manual_target`을 지정해야 한다. 다른 출처/외부 ID 문서의 UUID는 대조 대상으로
받지 않는다. 모집 시작일은 현재 계약에 없으므로 기간이 모호한 자료를 자동
동일 공고로 합치지 않는다. 제목/URL 등이 달라진 기존 자료를 수정할 때도
대상 UUID를 명시해야 한다. 출처 간 유사 공고는 자동 병합하지 않는다.
수동 확인 UI·인가와 실제 자료 입력은 #51/#53에서 연결한다.

## 검증·운영 범위

실제 Alembic 마이그레이션을 적용한 SQLite와 PostgreSQL에서 생성·갱신·트리거,
커밋 응답 유실 후 재시도·실패 롤백, 수동 대조·출처 격리·중요 필드별 공개 보류를
시험한다. PostgreSQL 다중 연결에서 12개 최초 수집과 12개 변경 수집을 동시에
실행해 단일 문서·빈틈 없는 버전 번호·최신 관측 보존을 확인한다. SQLite의
`FOR UPDATE`를 분산 동시성 증거로 사용하지 않는다.

실제 출처 정규화기/스케줄러·운영자 API 연결, 실제 공고 수집 및 배포는 후속 작업이다.
시험 관측은 가상 공고이며 생산 수집이 완료됐다고 주장하지 않는다.
