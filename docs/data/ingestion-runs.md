# 제한 수집 실행·집계·재개 (W06-06 · #49)

`python -m app.collect`는 한 출처의 안전 수집 → 정규화 → pending 버전 저장을 연결하는 운영자 명령이다. 인터넷에 실행 API를 공개하지 않는다. [수집](safe-fetch.md)·[정규화](normalization.md)·[버전 저장](ingestion-versions.md)의 검증/공개 승인 경계를 유지한다.

## 실행 준비

1. `backend/`의 해시 잠금 의존성을 설치하고 DB 마이그레이션을 `head`까지 적용한다. 새 `0003_ingestion_state`는 일일 요청 수·재개 페이지·검수 메타데이터와 실행별 요청/거절 사유 집계를 추가한다.
2. 운영 DB는 기존 설정대로 CA·호스트 검증 TLS를 사용한다. 개발/시험 이외에는 검증을 끄지 않는다.
3. DB의 `sources`에 해당 출처가 등록·활성화되어 있어야 한다. `code`는 `senuri` 또는 `volunteer`, `base_url`은 [확인된 공식 API](field-mapping.md#1-출처-설정)와 정확히 일치해야 한다. 명령은 URL을 받지 않는다.
4. `DATABASE_URL`, `DATA_GO_KR_SERVICE_KEY`는 루트 `.env` 또는 실행 환경에서 읽는다. 인증키는 `SecretStr`로 다루고 인자/출력/실행 테이블에 넣지 않는다. 실제 유효 키·기관별 승인 한도는 운영자가 확인한다.

```bash
cd backend
python -m alembic upgrade head
python -m app.collect --source <출처-UUID> --max-requests 25 --max-pages 10 --rows 10
python -m app.collect --source <출처-UUID> --max-requests 25 --due
```

`--help`에서 인자를 확인한다. 요청 수 1~10,000, 페이지 수 1~100, 행 수 1~100이다. 한 번의 네트워크 실행은 최대 600초다. 키가 없거나 DB/설정 오류가 나면 원문 예외를 출력하지 않는다. 실행 출력은 상태·실행 UUID·고정 실패 코드뿐이다. 완료/건너뜀은 종료 0, 실패/설정 불가는 1, 사용자 중단은 130이다.

## 잠금과 DB 수명

- 출처 UUID로 namespaced 64bit 잠금 키를 만들고 PostgreSQL `pg_try_advisory_lock`을 사용한다. 인증/암호 키가 아니다. 같은 출처의 동시 실행은 `skipped`이며 다른 출처는 독립적으로 실행할 수 있다.
- 전용 연결의 **세션** 잠금을 유지하고 외부 I/O 중 DB 트랜잭션/행 잠금을 열어 두지 않는다. 종료 시 연결을 폐기해 잠금이 pool에 남지 않게 한다. CLI는 NullPool을 사용한다.
- 프로세스가 강제 종료되어도 DB 연결이 닫히면 잠금이 풀린다. 다음 잠금 소유자는 이전 running 실행을 cancelled 실패로 마무리하고 새 실행을 만든다. 다른 살아 있는 소유자의 실행을 만료 시간만 보고 탈취하지 않는다.
- DB 상태 작업은 statement 5초·행 잠금 대기 1초로 제한한다. 저장 트랜잭션에도 같은 로컬 제한을 적용한다. HTTP 자체의 DNS/I/O/본문 제한은 #45 규칙을 따른다.
- SQLite는 단위 시험의 저장/집계에만 쓴다. 운영 실행 잠금을 SQLite로 대체하지 않는다.

## 출처 제한과 재개

- 코드에서 확인한 개발계정 상한은 노인 구인정보 10,000회/일, 1365 1,000회/일이다. 목록과 상세를 모두 차감하며 **요청 전에 DB commit**한다. 실패·프로세스 중단 후 사용량을 돌려주지 않는다.
- `--max-requests`는 실행당 더 낮은 예산이다. 한국 날짜 기준의 출처 일일 사용량은 별도로 영속 보존한다. 날짜가 앞으로 넘어갈 때만 초기화하며 시계가 뒤로 가면 예산을 복구하지 않는다. 같은 키를 사용하는 다른 시스템의 요청은 알 수 없으므로 실제 승인 한도/공유 사용량도 운영자가 관리해야 한다.
- 페이지 전체를 처리한 뒤 다음 페이지를 저장한다. 중간에 실패하면 같은 페이지를 다시 읽는다. 이미 저장한 공고는 출처/ID와 콘텐츠 해시로 중복 버전 생성을 막는다.
- 페이지/요청/일일 예산에 걸리면 `incomplete`/`budget_exhausted` 실패로 남기며 다음 실행에서 재개한다. 일부만 읽고 전체 성공 시각을 갱신하지 않는다.
- `totalCount`와 페이지별 예상 행 수가 맞지 않는 짧은 응답도 성공 완료로 처리하지 않는다. 실제 표본의 페이지 계약이 다르면 별도 검토 후 지원한다.
- 출처 한도가 6시간 전체 갱신보다 우선한다. 큰 최초 수집은 여러 날이 걸릴 수 있으며 모든 원문이 매 6시간 새로 확인된다고 보장하지 않는다.

## 집계와 데이터 상태

`IngestionRun`에는 fetched/created/changed/rejected/request 건수, 거절 사유 코드별 건수, 시작/종료/상태/실패 코드를 남긴다. 원문·연락처·URL·API 키를 로그나 실행 집계에 넣지 않는다. 사유 없는 잘못된 ID·중복 ID는 고정 코드로 처리한다.

- 모든 API 페이지를 정상적으로 읽고 처리하면 succeeded다. 정규화에서 제외/보류된 행은 rejected 집계에 남긴다. 이 성공은 모든 공고의 공개 승인이나 검수 완료를 뜻하지 않는다.
- 성공할 때만 출처의 `last_success_at`을 전진시키고 다음 페이지를 1로 되돌린다. API/키/네트워크/파싱/예산/저장 실패는 이전 성공 시각을 유지한다. 빈 정상 API 결과와 실패를 구분한다.
- 실패/일시 누락 때문에 이전 공고를 모집 종료로 바꾸지 않는다. API 실패에서는 기존 버전과 공개 포인터를 유지한다.
- 정상 XML의 기존 공고가 현재 정규화 기준을 충족하지 못하면, 이전 내용을 복사했다는 검수 메타데이터와 `unknown` 상태의 새 pending 버전으로 추천/생성을 보류한다. 이전 승인 공개본은 유지하며 새 사실을 확인했다고 표시하지 않는다. Source 잠금 안에서 최신 내용을 읽어 동시 편집을 오래된 내용으로 덮어쓰지 않는다. 이전 마감일 자체가 지난 경우의 종료는 기존 수명 규칙을 따른다.
- 새 버전과 `IngestionReview`의 미확인 코드·검수 사유를 같은 트랜잭션으로 저장한다. 메타데이터 저장이 실패하면 새 버전도 rollback한다. 오래된 수집 결과로 최신 검수 메타데이터를 덮어쓰지 않는다.

## 6시간 스케줄 인터페이스

`--due`는 DB의 다음 실행 시각을 확인한다. 성공 후 6시간, 실패 후 15분보다 이르면 건너뛴다. 같은 출처 실행 중/비활성/없는 출처도 건너뛰며 API를 호출하지 않는다. `--due` 없이 운영자가 재개해도 일일 예산과 같은 출처 잠금은 우회하지 못한다.

이 PR은 OS cron·유료 스케줄러·Codex 자동화를 설치하지 않는다. #96의 스케줄러가 출처별로 이 명령을 호출하고 한도/재개/실패 상태를 확인하는 인터페이스다.

## 검증 범위

실제 PostgreSQL에 0001~0003 마이그레이션을 적용해 실행/재개·예산·시간 역행·중복 버전·검수 메타데이터 rollback·취소·같은/다른 출처 잠금·실제 작업 프로세스 종료 후 복구·행 잠금 대기 제한을 확인했다. 유효 키 대신 시험용 값으로 실제 CLI/HTTPS 요청을 실행해 403 실패 집계와 기존 성공 시각 보존을 확인했다.

정상 수집 파이프라인은 가상 공고로 검증했다. 유효 키의 실제 정상 수집·공식 필드/코드표 검수·EC2 운영 스케줄은 미검증이다. 운영 동의문/실제 시작 비활성 조건과 별개이며 운영 배포 완료로 표시하지 않는다.

## 수도권 봉사 목록 재개

1365 목록은 `getVltrAreaList`에 `schSido`를 지정해 서울(`6110000`) → 경기(`6410000`) → 인천(`6280000`) 순으로 읽는다. 세 지역은 같은 출처 잠금과 일일 요청 예산을 공유하며 목록·상세 요청을 모두 차감한다. 인천 코드는 기존 필드 매핑 기준이며 실제 응답 표본 검증은 운영 준비에서 별도로 확인한다.

`0008_volunteer_region`은 수집 상태에 `region_index`를 추가한다. 배포 시 수집 프로세스를 멈추고 마이그레이션과 새 코드를 함께 적용한다. 기존 전국 봉사 목록의 페이지는 지역 페이지와 호환되지 않아 서울 1페이지로 초기화하며, 일일 사용량·기존 공고·성공 이력과 다른 출처 페이지는 보존한다. 다운그레이드도 봉사 페이지만 초기화한다.

지역과 다음 페이지는 함께 저장한다. 페이지 처리 도중 실패하면 같은 지역·페이지를 다시 읽으며 기존 버전 중복 방지를 사용한다. 빈 지역은 다음 지역으로 이동하고 세 지역을 모두 마친 경우에만 성공 시각을 갱신한다. `max_pages`는 지역 전체에서 공유하는 한 번의 실행 제한이며, 한도 도달 시 다음 실행이 저장된 지역·페이지에서 이어진다.
