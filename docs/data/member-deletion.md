# 저장 자료 삭제·동의 철회·탈퇴 (#78)

서버가 확인한 자기 회원만 `DELETE /profiles/me`, `DELETE /drafts/{document_id}`를 사용할 수 있다. 프로필 삭제는 모든 프로필 버전과 파생 지원서 전 버전을 포함한다. 지원서 삭제는 선택 문서의 전 버전만 지우며 다른 저장 문서·프로필은 유지한다. 운영자 역할도 다른 회원의 자료 삭제 권한을 주지 않는다. 없는 프로필은 204, 없는 지원서·다른 회원 지원서는 같은 404다. 삭제 요청의 임의 본문·쿼리 주체는 거절한다.

`POST /consents/withdraw`는 목적별로 처리한다. `storage`는 회원 저장 프로필·파생 지원서를 지우고 저장 동의를 철회한다. `ai_processing`은 모든 기존 임시 체험을 지우고 AI 동의만 철회하며 회원 저장본은 유지한다. 익명 AI 철회는 현재 세션의 임시 체험·동의를 단일 Redis 실행으로 지운다. 수락한 적 없거나 이미 철회한 회원 목적은 삭제0건으로 성공하며 다른 목적의 활성 체험·세션을 바꾸지 않는다.

`DELETE /me`는 현재 세션이 5분 이내 카카오 재인증을 마친 경우만 허용한다. 계정·제공자 연결·동의·저장 자료·저장 응답 기록을 삭제한다. 재가입하면 새 내부 사용자 UUID를 만들며 이전 자료를 연결하지 않는다. 실제 카카오 정상 승인과 운영 안내문은 별도 검증이고 예제 동의를 활성화하지 않는다.

## 저장 경합과 세션

삭제는 저장과 같은 User 행 잠금으로 직렬화한다. 첫 트랜잭션은 삭제 요청과 새 세션 세대를 `pending`으로 영속화한다. `pending` 또는 `failed`가 있으면 로그인과 회원 업무를 차단하며 오래된 세대의 세션도 사용할 수 없다. 새 회원 세션은 계정별 최대 16개 인덱스에 등록한다. 인덱스와 세대를 갖추지 못한 과거 인증은 거절한다. 배포 전 기존 서버를 배출하고 기존 인증 Redis 자료를 정리해야 한다.
같은 기기의 로그인 교체는 기존 슬롯을 재사용한다. 만료된 세션의 남은 임시 자료와 인덱스를 소유권 검사 후 정리해 새 로그인을 막는 만료 슬롯이 쌓이지 않게 한다. 현재 계정의 pending/failed 검사는 회원·상태 복합 인덱스로 조회한다.

두 번째 단계는 DB 밖 최소 삭제 이력을 내구 저장한 뒤 모든 기존 회원 세션·체험·대기·연결 응답을 Redis의 한 실행에서 정리하고 SQL 자료 삭제와 `completed`를 커밋한다. 각 세션 체험60개·체험 요청256개 제한과 소유권을 모두 검증한 뒤 삭제한다. 모든 세션의 임시 편집 자료를 초기화해 이전 승인·대기·늦은 저장이 자료를 재생성하지 못하게 한다. 호출자는 탈퇴를 제외하면 새 주체·CSRF의 회원 세션으로 전환하며 다른 기기는 다시 로그인한다.

진행 중이던 SQL 저장이 먼저 끝나면 삭제가 그 결과를 포함해 지운다. 삭제 대기가 먼저 확정되면 이전 세션의 저장은 거절한다. 단순 조회·직접 편집도 현재 회원 상태·세대를 검사한다. Redis 정리 이후 늦은 결과는 기존 수명/주체 검사를 통과하지 못한다. SQL/Redis/파일을 하나의 분산 트랜잭션이라고 주장하지 않는다.
회원 동의 수락·조회도 전달받은 서버 세션의 세대를 SQL User 잠금 안에서 재검사한다. 철회 전에 권한 검사만 통과한 늦은 수락이 철회 후 동의를 되살리지 못하게 한다. 새 세션에서 다시 수락한 동의는 과거 철회 이력을 복구에 재적용해도 유지한다.

외부 이력·Redis·SQL 실패 시 완료를 응답하지 않으며 영속 `pending`/`failed`를 재시도한다. 응답 유실이나 마지막 쿠키 교체 실패가 발생하면 실제 삭제가 완료되었을 수도 있어 로그인 상태와 저장 자료를 다시 확인해야 한다. 계정 처리가 차단된 실패는 운영 관리 재시도가 필요하다. 처리하지 않은 실패를 단순 상태 변경으로 숨기면 안 된다.

## 최소 이력과 개발 검증 위치

SQL `deletion_records`와 별도 이력에는 요청 UUID, 내부 회원/대상 UUID, 고정 범위·행위, 세대, 시각·만료만 둔다. 본문·공고 제목·카카오 식별자·토큰·암호문·오류 메시지를 넣지 않는다. 기존 설계 기본값대로 만료는 요청 시각부터 30일이며 계정 FK로 삭제되지 않는다.

`DELETION_JOURNAL_DIRECTORY`는 서버가 지정한 절대 경로다. **APP_ENV=development의 POSIX 검증용 파일 어댑터만** 제공한다. 현재 프로세스 uid 소유 0700 폴더, 0600 일반 파일, 경로별 symlink 거절, hardlink/FIFO/과대 파일 거절, 원자적인 새 파일 등록과 파일/폴더 fsync, 같은 요청의 원문 일치를 검사한다. DB 파일·RDS 백업과 분리한 검증 위치를 사용한다. HTTP 입력으로 경로를 받지 않는다. Windows와 production/test 설정에서는 이 개발 어댑터를 운영 삭제에 대신 사용하지 않는다.

운영 DB 밖 보관 위치·최소 권한·암호화·30일 보관/파기·최신 이력 복구를 검증한 운영 어댑터는 아직 필요하다. 설정이 없으면 실제 삭제 전에 503으로 거절한다. 운영 정보 미정을 임의 AWS 버킷·리전·정책으로 확정하지 않는다.

그래서 `APP_ENV=production`에서 삭제 이력 어댑터가 연결되지 않으면 `create_app`이 회원 저장 기능을 함께 닫는다. 저장 동의 버전(`STORAGE_NOTICE_VERSION`)과 공개 저장 안내문을 비활성으로 두고 카카오 로그인 어댑터를 만들지 않는다. `/consents/notices`의 `storage`는 `null`, `login_available`은 `false`가 되어 새 로그인·저장 화면이 열리지 않는다. 익명 체험과 AI 동의·철회는 그대로 동작한다. 저장은 되는데 탈퇴·삭제·저장 동의 철회가 503인 상태를 만들지 않기 위한 조건이며, 운영 어댑터를 연결하면 별도 설정 없이 다시 열린다. development·test 설정은 기존대로 동작한다.

## 관리 재시도·복구·만료

운영자 웹 권한을 우회하는 API는 없다. 권한이 제한된 서버 환경에서 같은 설정을 사용한다. 예외 원문이나 식별자를 출력하지 않고 처리 건수/고정 오류 코드만 출력한다.

```sh
cd backend
python manage_deletions.py retry --limit 100
# 복원 DB와 Redis를 공개하기 전에 최신 별도 이력을 준비해 재적용한다.
python manage_deletions.py recover --limit 1000
python manage_deletions.py prune
```

`retry`는 최대100개 pending/failed를 한 번에 처리한다. 한 건이라도 실패하면 성공으로 출력하지 않는다. `recover`는 최신 유효 이력의 대상 UUID에 삭제를 재적용하고 재수락한 동의(요청 이후 시각)·새 프로필/문서 UUID는 과거 요청으로 지우지 않는다. 이미 완료된 같은 기록도 복원에서는 다시 적용한다. **복원 재적용 동안 서비스를 중단하고 완료·자료 검증 뒤에만 공개한다.** 최소 이력30일과 암호화 백업7일 순환이 지켜져야 한다. 개발 파일 이력은 최대1000개를 제한 조회하며 초과/모호한 자료는 부분 성공으로 열지 않는다.

`prune`는 만료 파일과 완료 SQL 최소 이력을 정리한다. 미해결 SQL pending/failed를 지워 계정을 임의로 다시 열지 않는다. 만료된 미해결 요청은 운영 검토가 필요하다. 주기 실행·실패 알림·운영 복원 리허설은 #94/#96의 운영 검증과 연결해야 한다. 이 관리 명령 실행만으로 RDS·AWS 복구나 운영 보관 정책 검증을 완료했다고 주장하지 않는다.

## 시험

실제 PostgreSQL/Redis에서 자기 자료/다른 회원·CSRF·주체 위조, 전 버전과 파생 지원서 삭제, 여러 세션과 임시 체험 무효화, 목적별 철회, 현재 재인증 탈퇴, 외부 이력 실패 차단/재시도, 삭제 전 암호문 DB 스냅샷 복원 후 별도 이력 재적용, SQL 저장·삭제 경합을 검증한다. 파일 권한·심볼릭 링크·FIFO·hardlink·과대/잘못된 JSON도 시험한다. 가상 제공자·본문·키·안내문을 쓰며 운영 개인정보를 사용하지 않는다.
