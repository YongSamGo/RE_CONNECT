# 확정 프로필의 암호화 저장 — W10-04

## API와 승인 원본

`GET /api/v1/profiles/me`는 현재 세션의 서버 검증 User가 소유한 최신 저장본만 복호화한다. 없으면 saved=null이다. 읽기는 세션 유휴 수명을 연장하지 않는다. `POST /profiles/me/versions`는 Origin/서명 CSRF, HTTP 한도, UUID 멱등 키, 현재 회원/저장 동의를 검사한다. 두 응답 모두 Cache-Control: no-store다.

요청은 source와 base_saved_version뿐이다. source는 현재 세션의 체험 확정본 참조 또는 그 회원/세션에 결합한 일회 저장 대기다. 본문·소유자·승인 시각·암호화 메타데이터는 받지 않는다. 지원서를 포함한 대기는 명시적인 프로필 저장 요청으로 프로필만 먼저 저장하고, 지원서 대기는 원래 만료까지 보존한다. POST /drafts가 같은 승인 대기를 이어서 소비한다(#76). 지원서를 자동 저장하지 않는다.

회원은 SQL의 현재 AI 동의를 검사한 뒤 그 세션의 Redis 추론 guard에 같은 안내문을 결합하여 새 체험을 만들 수 있다. 익명 AI 동의를 상속하거나 회원 ID 헤더를 신뢰하지 않는다. 회원의 생성·메시지·지원서 추론 주체/계정 예산은 서버가 확인한 User다. 기존 저장본을 체험으로 가져오는 기능은 #42 후속이다.

## 새 버전·재사용·교체

User 행을 잠근 SQL 트랜잭션에서 현재 저장 동의와 기존 저장 버전을 검사한다. 저장본이 없으면 base_saved_version=null이며 기존 저장본이 있으면 정확한 현재 버전을 보내 교체를 확인해야 한다. 현재 본문과 같으면 새 버전 없이200/created=false이고, 다르면 새 버전을 INSERT하여201/created=true와 replaced_version을 반환한다. 기존 본문/시각은 덮어쓰지 않는다.

체험 참조는 실제 소유권/수명/현재 확정 버전을 쓰기 전후 다시 검사한다. 저장 대기는 정확한 회원/세션에서 한 번만 소비한다. 저장 후 세션도 재검사하며 로그아웃·체험 종료는 같은 PostgreSQL User 행 잠금 경계를 지나야 성공을 반환한다. 진행 중 쓰기 실패·취소·회수는 본문과 응답 기록을 함께 롤백한다.

## 암호화와 키

[본문 암호화](../security/encryption.md)의 ContentCipher를 사용한다. 소유자·종류·문서 ID·버전·스키마를 결합한 대상별 키/AAD와 임의12바이트 nonce로 AES-256-GCM 암호화한다. DB에는 암호문/nonce/key_id/알고리즘/스키마만 쓰며 키·평문을 기록하지 않는다. 다른 대상의 봉투·변조·필요한 키 없음은 고정503이다.

DATA_ENCRYPTION_KEYS와 DATA_ENCRYPTION_ACTIVE_KEY_ID는 비밀 설정에서 공급한다. 누락/오류를 임의 키 생성이나 평문 저장으로 대신하지 않는다. 현재 저장본을 복호화해야 같은 내용인지 비교할 수 있으므로 필요한 이전 키도 유지해야 한다. 시험 키는 실행마다 생성하는 가상 키이며 운영 키 생성·복구·배포의 증거가 아니다.

## 응답 재전송과 삭제

`profile_write_receipts`는 User+멱등 UUID 키의 입력 해시·대기 ID의 일회 전달 해시와 문서 ID/결과 버전/시각/생성·교체 여부/24시간 만료만 담는다. 프로필 본문·대화·원래 체험/대기 참조는 담지 않는다. 승인 암호문과 같은 SQL 트랜잭션에서 INSERT하며 UPDATE는 DB 트리거로 거절한다. 같은 회원의 만료 기록은 다음 쓰기에서 제거한다.

같은 키/입력의 완료 응답은 소비된 대기나 과거 base를 검사하기 전에 SQL에서 재전송한다. 현재 회원·저장 동의는 여전히 필요하다. 다른 입력이면 충돌이다. 같은 대기의 프로필 부분은 회원+대기 해시 고유 제약으로 한 번만 전달하며, 다른 요청 키로 재사용하면409다. 결과 프로필이 삭제되었으면 완료 기록으로 재생성하지 않고404다. 프로필 계열 삭제는 ProfileDocument를 삭제해야 하며 완료 기록은 만료까지 남는다. User 삭제는 그 회원의 기록도 cascade 삭제한다.

SQL/Redis 분산 트랜잭션은 없다. 대기 소비 뒤 SQL 실패/취소이면 저장본/응답 기록은 없고 대기를 되살리지 않는다. 사용자에게 다시 확인/발급을 요청해야 한다. 성공한 저장의 응답만 SQL 기록으로 재전송할 수 있다.

## 검증 범위

실제 Redis·SQLite/PostgreSQL·ASGI에서 암호문/nonce/소유권·동의·CSRF·교체 기준, 같은 내용 재사용·불변 버전, 소비 후 재전송·경합6개→1저장, 삭제 후 재생성 거절, SQL 오류/취소/로그아웃 롤백, 키 없음·봉투 변조를 시험한다. 실제 TCP API로 대기 저장·재전송·자기 조회·회원 새 체험 저장·같은 내용200도 확인한다.

제공자/안내문/키/본문은 가상 시험 데이터다. 실제 운영 정보 미정으로 실동의는 계속 비활성이고 실제 카카오 정상 승인·운영 HTTPS/EC2·키 보관·복구·기기 검증은 남아 있다. #76 지원서 결합 저장은 별도 모듈에 연결되며, #77 재편집, #78 삭제·철회·탈퇴, #79 접근·경합 검증은 후속이다.
