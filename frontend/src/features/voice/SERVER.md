# 체험 녹음·전사 확인 — #83 로컬 부분 연결

2026-10-24: 준비된 `/journeys/:journeyId/conversation`에서 녹음 후 별도 버튼으로 `POST /journeys/{journey_id}/transcriptions`를 요청한다. 기존 `/voice` 기기 내 미리보기는 서버로 보내지 않는다.

- 기존 녹음기의 형식 협상, 90초/6MiB 한도, 권한 취소·마이크 종료·object URL 정리를 재사용한다. 녹음 완료만으로 업로드하지 않는다.
- 전사 요청마다 현재 AI 처리 동의를 확인한다. multipart에는 음성 Blob 하나만 넣으며 임의 주소·사용자 ID를 받지 않는다. 응답 ID·문장 길이·유한한 음성 시간을 검증한다.
- 응답이 불확실하면 같은 키와 최초 음성으로 재확인한다. 확정된 모델/형식 실패 뒤 명시적으로 다시 요청하면 새 키를 발급한다. 새 녹음·취소·이탈 시 화면의 요청/전사 참조를 폐기한다.
- 전사 문장을 직접 수정하고 기존 입력이 있으면 교체 확인을 해야 입력란으로 가져올 수 있다. 이 동작은 메시지 전송이나 프로필 확정이 아니다. 대화의 별도 보내기 버튼이 수정 문장과 서버 전사 ID를 전달한다.
- 전사를 가져오거나 세션·동의·접근을 잃으면 녹음기를 다시 마운트해 음성과 재생 주소를 해제한다. 취소한 서버 처리가 이미 끝났을 가능성은 안내한다.

프론트 전체 471개/40파일과 lint·OpenAPI 타입·TypeScript·빌드 통과. 전용 전사 6개는 대역 녹음 버튼과 실제 API 클라이언트의 multipart 바이트/동의 차단/수정 확인/멱등 재확인/취소/파서를 검사한다. 대기 취소 뒤 늦은 본문 파싱 결과가 화면에 복원되지 않음을 확인했다. 대화와 실제 전사 화면을 함께 마운트한 별도 회귀는 수정·교체 확인·입력란 가져오기만으로 메시지가 전송되지 않고 별도 보내기에서 수정 문장·전사 ID·프로필 revision이 전달됨을 확인한다. 녹음기만 대역이고 두 화면과 API 클라이언트는 실제 코드다. 기존 녹음기 시험에 서버 전사 모드의 명시 요청·Blob 전달·취소 정리 1개를 추가했다. jsdom File과 Node Request의 혼용을 피하도록 전사 시험에서만 Node Blob/File/FormData를 맞췄다.

현재 backend에는 업로드 크기·CSRF 경계와 내부 음성 어댑터가 있지만 `/journeys/{journey_id}/transcriptions` 제품 라우터는 아직 없다. 이 화면은 계약 호출과 오류 처리까지의 부분 구현이며 실제 전사 성공 화면으로 계산하지 않는다. #38의 서버 전사 자료 수명·메시지 참조 연결과 실제 음성 서버 계약, TTS와 녹음의 상호 중지, 세 기기·실제 마이크·스크린리더 검증은 남아 있다. 운영 안내 미정으로 실제 동의·체험 시작은 계속 비활성이다. #83 전체 통과나 실제 기기 성공으로 기록하지 않는다.
