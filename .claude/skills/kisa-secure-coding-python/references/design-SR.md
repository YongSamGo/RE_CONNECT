## 1. 입력데이터 검증 및 표현

사용자와 프로그램의 입력 데이터에 대한 유효성 검증 체계를 갖추고, 유효하지 않은 값에 대한 처리방법을 설계한다.

### SR1-1. DBMS 조회 및 결과 검증

**설명**: DBMS 조회 시 질의문(SQL) 내 입력값과 그 조회결과에 대한 유효성 검증방법(필터링 등)을 설계하고, 유효하지 않은 값의 처리방법을 설계한다.

**요구사항 (원문)**
1. 애플리케이션에서 DB 연결을 수행할 때 **최소권한 계정**을 사용해야 한다.
2. 외부입력값이 삽입되는 SQL 쿼리문을 **동적으로 생성해서 실행하지 않도록** 해야 한다.
3. 외부입력값으로 동적 SQL을 생성해야 하는 경우, 입력값 검증 후 사용해야 한다.

**설계 시 고려사항**
- DB 계정은 해당 애플리케이션이 사용하는 테이블에 대한 읽기·쓰기·삭제·갱신 권한만 부여한다 (원문 예: 계정명 `애플리케이션명_시리얼번호`, 권한 범위 `애플리케이션명_테이블명`).
- SQL 구조가 외부 입력으로 바뀌지 않는 API(파라미터 바인딩)와 ORM을 쓰도록 시큐어코딩 규칙을 정한다.
- 검증은 클라이언트·서버 양쪽에서 하되, 서버 검증을 기준으로 삼는다. 일괄 적용 방식은 다음과 같다:
  - (ㄱ) Filter 컴포넌트 → `[Python 적용]` WSGI/ASGI 미들웨어, Django Middleware
  - (ㄴ) Interceptor → `[Python 적용]` Flask `before_request`, FastAPI dependency
  - (ㄷ) 공통 Validator → `[Python 적용]` pydantic 모델, Django Form/Serializer, marshmallow
- 원문의 대응 라이브러리는 Hibernate, MyBatis, JPA (Java), AntiSQLi (.NET), MeekroDB (PHP)이다. `[Python 적용]` SQLAlchemy ORM/Core, Django ORM, DB-API 파라미터 바인딩(`%s`, `?`, `:name`)으로 대응한다.

**점검 질문**
- [ ] DB 접속 계정이 superuser/root/`postgres`/`sa` 같은 관리자 계정이 아닌가? (설정 파일, `DATABASES`, `SQLALCHEMY_DATABASE_URI`, 환경변수 확인)
- [ ] 문자열 연결·f-string·`%`·`.format()`으로 SQL을 만드는 코드가 없는가? (→ INP-01)
- [ ] `text()`, `raw()`, `extra()`, `RawSQL`, `cursor.execute()` 사용처마다 바인딩을 쓰는가?
- [ ] 동적으로 바꿔야 하는 테이블명·컬럼명·정렬 방향은 허용목록(allowlist)으로 선택하는가?
- [ ] 입력 검증이 공통 계층(pydantic 스키마, Form, Serializer)에 모여 있는가?

### SR1-2. XML 조회 및 결과 검증

**설명**: XML 조회 시 질의문(XPath, XQuery 등) 내 입력값과 그 조회결과에 대한 유효성 검증방법을 설계한다.

**요구사항 (원문)**
1. XML 문서를 조회할 때 XML 질의에 쓰이는 파라미터는 질의를 조작할 수 없도록 **필터링**하거나, 미리 작성된 질의문에 **자료형에 따라 바인딩**해서 사용해야 한다.

**설계 시 고려사항**
- (ㄱ) 공통 Validator로 XML 삽입 문자열을 필터링한다.
- (ㄴ) Filter 컴포넌트에서 `"`, `[`, `]`, `/`, `=`, `@` 를 필터링한다.
- (ㄷ) 개별 코드에서 위 문자를 제거하거나 안전하게 치환하는 규칙을 정한다.
- (ㄹ) 외부 입력이 질의 구조를 바꿀 수 없는 API를 쓰도록 규칙을 정한다. `[Python 적용]` `lxml`의 XPath 변수 바인딩 `tree.xpath("//user[@id=$uid]", uid=value)`
- 원문 사고사례는 XML 파서 설정이 취약해 서버 파일이 노출된 경우(XXE)다. 파서 보안 설정도 설계 범위에 넣는다 (→ INP-08).

**점검 질문**
- [ ] XPath/XQuery를 문자열 연결로 만드는 코드가 없는가?
- [ ] `lxml`·`xml.etree`·`xml.dom.minidom`·`xml.sax`로 외부 XML을 파싱할 때 `defusedxml`을 쓰거나 외부 엔티티를 막는가?
- [ ] XML 조회 결과를 그대로 응답에 쓰지 않고 검증·인코딩하는가?

### SR1-3. 디렉토리 서비스 조회 및 결과 검증

**설명**: 디렉토리 서비스(LDAP 등)를 조회할 때 입력값과 조회결과의 유효성 검증방법을 설계한다.

**요구사항 (원문)**
1. LDAP 인증서버로 인증을 구현할 때, 인증 요청에 쓰이는 외부입력값은 LDAP 삽입 취약점이 없도록 필터링해서 사용해야 한다.

**설계 시 고려사항**
- 외부 입력이 LDAP 검색 필터에 들어가면 필터 규칙으로 해석될 수 있는 특수문자(`=`, `+`, `<`, `>`, `#`, `;`, `\` 등, 그리고 `*`, `(`, `)`, NUL)를 제거하거나 이스케이프하는 규칙을 정한다.
- `[Python 적용]` `ldap3.utils.conv.escape_filter_chars()`, python-ldap의 `ldap.filter.escape_filter_chars()`, DN에는 `ldap.dn.escape_dn_chars()`를 쓴다.

**점검 질문**
- [ ] `search_filter`, `search_s`, `search()` 인자에 입력값이 이스케이프 없이 들어가지 않는가? (→ INP-10)
- [ ] LDAP 바인드 계정이 최소권한이고, 익명 바인드를 허용하지 않는가?

### SR1-4. 시스템 자원 접근 및 명령어 수행 입력값 검증

**설명**: 시스템 자원 접근이나 명령어 실행 시 입력값의 유효성 검증방법을 설계한다.

**요구사항 (원문)**
1. 외부입력값으로 시스템 자원(IP, 포트, 프로세스, 메모리, 파일 등)을 식별할 때 허가되지 않은 자원이 쓰이지 않도록 해야 한다.
2. 서버 프로그램에서 쉘을 생성해 명령어를 실행해야 하는 경우, 외부입력값으로 악의적인 명령이 실행되지 않도록 해야 한다.

**설계 시 고려사항**
- 외부 입력이 내부 리소스를 **직접 결정하지 않도록** 설계한다. 사용할 리소스 목록을 정의하고 그 안에서 선택하게 한다. 목록은 설정 파일(원문: properties/XML → `[Python 적용]` YAML/TOML/JSON, `settings.py`)로 관리해 변경 시 코드 수정을 줄인다.
- 특정 디렉토리의 모든 파일처럼 목록화가 어려우면, 경로조작 문자(`..`, `/`, `\`)를 제거하고 지정 경로 안의 파일만 접근하게 한다. `[Python 적용]` `Path(base).joinpath(name).resolve()`가 `base.resolve()` 아래인지 `is_relative_to()`로 확인한다.
- 쉘 명령 실행 구조 자체를 피하는 것이 우선이다. 불가피하면 명령 구성요소를 허용목록으로 정의하고, 외부 입력은 **목록 인덱스(선택자)**로만 쓴다.
- `[Python 적용]` `subprocess.run([...], shell=False)` 리스트 인자 사용, `os.system`/`os.popen`/`shell=True` 금지, `eval`/`exec` 금지.

**점검 질문**
- [ ] `open()`, `send_file()`, `FileResponse`, `os.remove()` 등에 들어가는 경로가 외부 입력에서 오지 않는가? 온다면 기준 디렉토리 검증이 있는가? (→ INP-03)
- [ ] `os.system`, `os.popen`, `subprocess.*(shell=True)`, `commands`, `pty.spawn` 사용처가 없는가? (→ INP-05)
- [ ] `eval`, `exec`, `compile`, `__import__`, `importlib.import_module`에 외부 입력이 들어가지 않는가? (→ INP-02)
- [ ] 외부 URL/호스트로 서버가 요청을 보낼 때 허용목록이 있는가? (→ INP-12)
- [ ] 소켓 바인드 IP·포트, 연결 대상 호스트를 입력값으로 정하지 않는가?

### SR1-5. 웹 서비스 요청 및 결과 검증

**설명**: 웹 서비스(게시판 등) 요청(스크립트 게시 등)과 응답결과(스크립트가 포함된 웹 페이지)의 유효성 검증방법을 설계한다.

**요구사항 (원문)**
1. 사용자 입력값을 동적으로 생성되는 응답페이지에 쓸 경우 XSS 필터링 후 사용해야 한다.
2. DB 조회결과를 동적으로 생성되는 응답페이지에 쓸 경우 HTML 인코딩 또는 XSS 필터링 후 사용해야 한다.

**설계 시 고려사항**
- 입력 측: 필터(미들웨어)·인터셉터·공통 Validator로 XSS 필터링이나 HTML 인코딩을 일괄 적용한다.
- 출력 측: View 컴포넌트(`[Python 적용]` Jinja2/Django 템플릿)에서 출력값을 인코딩하는 규칙을 정한다.
- **DB에서 읽은 데이터도 외부 입력으로 간주**한다 (Stored XSS). 프레임워크로 일괄 처리하기 어려우니 출력 시점 인코딩을 개발가이드에 명시한다.
- 원문의 라이브러리는 MS Anti-XSS, HtmlSanitizer, LUCY XSS Filter, OWASP ESAPI, HTML Purifier다. `[Python 적용]` Jinja2 autoescape, Django 템플릿 자동 이스케이프, `markupsafe.escape`, `html.escape`, HTML 허용이 필요하면 `nh3`(또는 `bleach`) 허용목록 sanitizer를 쓴다.

**점검 질문**
- [ ] Jinja2 `Environment(autoescape=...)`가 켜져 있는가? Flask `render_template_string`에 사용자 입력이 들어가지 않는가?
- [ ] 템플릿에 `|safe`, `{% autoescape off %}`, `Markup()`, `mark_safe()`, `format_html` 오용이 없는가?
- [ ] 문자열 연결로 HTML을 만들어 `HttpResponse`/`make_response`로 반환하지 않는가?
- [ ] Content-Type이 명확하고, 응답 헤더에 CSP가 설정되어 있는가?

### SR1-6. 웹 기반 중요기능 수행 요청 유효성 검증

**설명**: 비밀번호 변경, 결제 등 권한 확인이 필요한 중요기능을 수행할 때 요청의 유효성 검증방법을 설계한다.

**요구사항 (원문)**
1. 시스템으로 전송되는 모든 요청이 정상 사용자의 유효한 요청인지 판별할 수 있어야 한다.

**설계 시 고려사항**
- (ㄱ) **CSRF 토큰**: 세션별로 토큰을 만들어 세션에 저장하고, 작업 페이지에 hidden 값으로 내려준 뒤 처리 요청 시 비교한다. 검증은 프레임워크 컴포넌트(인터셉터)로 자동화한다. 원문은 Python 환경에 **Django**의 CSRF 방어 기능을 명시한다. `[Python 적용]` Flask는 Flask-WTF `CSRFProtect`, FastAPI는 double-submit 쿠키나 `fastapi-csrf-protect`, SameSite 쿠키를 함께 쓴다.
- (ㄴ) XSS가 있으면 CSRF 토큰이 무력화될 수 있으므로 CAPTCHA 같은 **사용자 상호작용 기법**을 쓴다.
- (ㄷ) 중요기능은 **재인증**으로 실제 요청인지 확인한다.

**점검 질문**
- [ ] Django `CsrfViewMiddleware`가 활성화되어 있고 `@csrf_exempt`가 남용되지 않았는가?
- [ ] Flask/FastAPI에서 상태 변경 엔드포인트(POST/PUT/PATCH/DELETE)에 CSRF 검증이 있는가?
- [ ] GET 요청으로 상태가 바뀌는 엔드포인트가 없는가?
- [ ] 비밀번호 변경·결제·권한 변경에 재인증이나 추가 확인 절차가 있는가?
- [ ] 세션 쿠키의 `SameSite`가 `Lax` 또는 `Strict`인가?

### SR1-7. HTTP 프로토콜 유효성 검증

**설명**: 비정상 HTTP 헤더, 자동연결 URL 링크 등 사용자가 원하지 않는 결과를 만드는 HTTP 헤더·응답결과의 유효성 검증방법을 설계한다.

**요구사항 (원문)**
1. 외부입력값을 쿠키나 HTTP 헤더정보로 쓸 경우 HTTP 응답분할 취약점이 없도록 필터링해서 사용해야 한다.
2. 외부입력값을 페이지 이동(리다이렉트·포워드) URL로 써야 하면, 그 값은 **허용된 URL 목록의 선택자**로 쓰도록 해야 한다.

**설계 시 고려사항**
- 응답 헤더에 들어가는 외부 입력에서 `\r\n`을 반드시 제거하는 규칙을 정한다 (쿠키 설정, 응답 헤더 설정, 리다이렉트 Location 포함).
- 허용 URL 목록은 소스코드나 설정 파일에 두고, 그 목록의 URL로만 이동하게 한다.
- `[Python 적용]` Django `url_has_allowed_host_and_scheme()`, 내부 경로만 허용할 때는 `urllib.parse.urlparse()`로 scheme·netloc이 비어 있는지 확인한다.

**점검 질문**
- [ ] `redirect(request.args["next"])`, `HttpResponseRedirect(request.GET[...])`처럼 검증 없는 리다이렉트가 없는가? (→ INP-07)
- [ ] `response.headers[...] = 입력값`, `set_cookie(..., 입력값)`에 CR/LF 제거가 있는가? (→ INP-13)

### SR1-8. 허용된 범위 내 메모리 접근

**설명**: 프로세스에 허용된 범위의 메모리 버퍼에만 접근하도록 검증방법을 설계하고, 범위를 벗어난 요청의 처리방법을 설계한다.

**요구사항 (원문)**
1. C/C++처럼 메모리를 직접 관리하는 플랫폼에서는 버퍼 경계를 넘어 읽거나 쓰지 않도록 경계 설정이나 검사를 해야 한다.
2. 버퍼 오버플로우를 일으킬 수 있는 취약한 API를 쓰지 않도록 통제해야 한다.

**설계 시 고려사항**
- 실행 환경에 Non-executable Stack, ASLR, StackGuard 같은 메모리 보호 정책을 적용한다.
- `[Python 적용]` 순수 Python 코드는 메모리 안전하지만, 다음 경우는 이 항목 대상이다: `ctypes`/`cffi` 사용, C 확장 모듈(Cython 포함) 작성, `struct.pack_into`/`memoryview`/`bytearray` 슬라이스 직접 조작, `mmap`. 포맷스트링은 Python에서도 `str.format()`에 사용자 제어 포맷이 들어가면 객체 속성 노출 문제가 생긴다 (→ INP-17).

**점검 질문**
- [ ] `ctypes.memmove`, `ctypes.create_string_buffer`, `ctypes.cast`, `cffi` 사용처에서 길이 검증이 있는가? (→ INP-16)
- [ ] 사용자 입력이 포맷 문자열 자체(`user_fmt.format(...)`, `user_fmt % ...`)로 쓰이지 않는가? (→ INP-17)

### SR1-9. 보안기능 입력값 검증

**설명**: 보안기능(인증, 권한부여 등)의 입력값과 함수의 외부입력값·수행결과에 대한 유효성 검증방법을 설계한다.

**요구사항 (원문)**
1. 사용자의 역할·권한을 결정하는 정보는 **서버에서 관리**해야 하며, 클라이언트가 보낸 식별정보는 검증 후 사용해야 한다.
2. 쿠키·환경변수·파라미터 등 외부입력값이 보안기능 함수의 인자로 쓰이면 검증 후 제한적으로 사용해야 한다.
3. 중요 상태정보나 인증·권한결정 정보는 쿠키로 전송하지 않아야 하며, 불가피하면 암호화해서 전송해야 한다.

**설계 시 고려사항**
- 상태·인증·인가·권한 정보는 서버 세션이나 DB에서 관리한다. 외부 인증 서비스 연동 시에도 **백채널 인증**으로 결과를 서버에서 검증한다.
- 비회원 로그인·간편인증처럼 식별자가 클라이언트에서 서버로 오는 구조는 특히 위험하다. 식별자를 암호화해도 **암·복호화를 클라이언트에서 하면** 같은 방식으로 우회된다.
- 보안기능은 외부 입력에 최대한 의존하지 않게 설계한다. 위·변조, 재생 공격, 호출 흐름 변경·생략을 고려하고, 사용 전 NULL(None) 여부를 확인한다.
- 중요정보가 담긴 쿠키는 서버에서 암호화하고 클라이언트에서 복호화하지 않는다. 무결성이 중요하면 서버가 **HMAC**을 만들어 붙이고 서버에서 검증한다. `[Python 적용]` `itsdangerous`, Django `signing`, `hmac.compare_digest`.
- 정수형 오버플로우, Null 역참조도 이 설계항목에 연결된다.

**점검 질문**
- [ ] `request.cookies["role"]`, `request.args["is_admin"]`, 헤더 값, hidden 필드로 권한을 판단하는 코드가 없는가? (→ INP-15)
- [ ] JWT를 쓴다면 서명 검증(`verify_signature`)을 끄지 않았고, `algorithms`를 명시하며 `none`을 허용하지 않는가?
- [ ] OAuth/소셜 로그인 결과를 클라이언트가 보낸 값 대신 서버가 토큰 검증으로 확인하는가?
- [ ] 외부 입력의 숫자 범위(수량, 금액, 페이지 크기)를 검증하는가? (→ INP-14)
- [ ] `None` 가능성이 있는 반환값(`dict.get`, `re.match`, ORM `.first()`)을 확인 없이 쓰지 않는가? (→ COD-01)

### SR1-10. 업로드·다운로드 파일 검증

**설명**: 업로드·다운로드 파일의 무결성, 실행권한 등에 대한 유효성 검증방법과 부적합한 파일의 처리방법을 설계한다.

**요구사항 (원문)**
1. 업로드되어 저장되는 파일의 **타입, 크기, 개수, 실행권한**을 제한해야 한다.
2. 업로드되어 저장되는 파일은 **외부에서 식별되지 않아야** 한다.
3. 파일 다운로드 요청 시 요청 파일명을 검증해야 한다.
4. 다운로드받은 소스코드나 실행파일은 **무결성 검사**를 해야 한다.

**설계 시 고려사항**
- (크기) 프레임워크 설정으로 제한한다. 원문 예는 Spring `maxUploadSize=20MB`, `maxInMemorySize=1MB`다. `[Python 적용]` Flask `MAX_CONTENT_LENGTH`, Django `DATA_UPLOAD_MAX_MEMORY_SIZE`/`FILE_UPLOAD_MAX_MEMORY_SIZE`, 리버스 프록시 `client_max_body_size`.
- (타입) 서버·클라이언트가 같은 정책을 쓰고, **MIME 타입과 확장자를 함께** 검사하는 공통모듈을 둔다. `[Python 적용]` 확장자 허용목록 + `python-magic` 등으로 실제 내용 검사.
- (실행권한) 업로드 디렉토리에 실행권한을 주지 않고, 웹서버 설정으로 업로드 경로의 파일이 실행되지 않게 한다.
- (비식별) 저장 경로는 URL로 직접 접근할 수 없는 디렉토리(웹 루트·`static/` 밖)로 하고, 다운로드는 별도 컨트롤러를 거치게 한다. 저장 파일명은 **랜덤 생성**(`uuid4`, `secrets.token_hex`)하고, 원본 파일명과의 매핑은 DB에 저장한다.
- (다운로드) 파일명의 `..`, `/`, `\`를 제거하고, 허가된 사용자·허가된 파일인지 확인하며, 다운로드 가능 파일을 화이트리스트로 관리한다. 악성코드 검사 후 제공하는 것을 고려한다.
- (무결성) 원격 파일을 쓰거나 실행할 때는 체크섬(해시)도 함께 받아 검증한다.

**점검 질문**
- [ ] 업로드 처리에서 확장자 허용목록, 크기 제한, 개수 제한이 모두 있는가? (→ INP-06)
- [ ] `werkzeug.utils.secure_filename` 또는 랜덤 이름을 쓰고, 원본 파일명을 그대로 저장 경로에 쓰지 않는가?
- [ ] 업로드 파일이 `static/`, `media/`처럼 웹에서 바로 접근되는 경로에 저장되지 않는가? (Django `MEDIA_URL` 노출 정책 확인)
- [ ] 다운로드 엔드포인트가 인증·인가 확인 후 파일을 제공하는가?
- [ ] `pip install`·`urllib`·`requests`로 받은 코드나 바이너리를 해시·서명 검증 없이 실행하지 않는가? (→ SEC-15, SEC-10)

## 2. 보안기능

인증, 접근통제, 권한관리, 비밀번호 등의 정책이 적절하게 반영되도록 설계한다.

### SR2-1. 인증 대상 및 방식

**설명**: 중요정보·기능의 특성에 따라 인증방식을 정의하고, 정의된 인증방식을 우회하지 못하게 설계한다.

**요구사항 (원문)**
1. 중요기능이나 리소스에는 "**인증 후 사용**" 정책을 적용해야 한다.
2. 안전한 인증방식을 써서 인증우회나 권한상승이 발생하지 않도록 해야 한다.
3. 중요기능에는 **2단계(2-factor) 인증**을 고려해야 한다.

**설계 시 고려사항**
- 분석단계에서 분류한 중요기능에 인증 후 사용 정책을 **중앙집중식으로 일괄 적용**한다 (기능별 개별 구현은 누락되기 쉽다).
- 인증정보는 서버 측에 저장하고, 접근 시도 때마다 서버가 인증 여부를 확인한다.
- 일회용 패스워드(OTP) 도입 시 원문의 규칙:
  - A. 시각정보, 이벤트정보, 질의-응답 방식으로 얻은 정보로 생성할 수 있다.
  - B. 시각 기반 연계정보는 특정 시간 동안만 유효해야 하고, 이벤트·질의-응답 방식은 연계정보를 추측할 수 없게 보호해야 한다.
  - C. 시간 제한을 둔다 (금융영역 30~60초).
  - D. 중복·유추가 불가능하도록 **6자리 이상** 숫자·문자로 구성한다.
  - E. OTP 발생기와 인증서버가 같은 정보를 생성해야 한다.
- 2단계 인증: Type1(지식: 패스워드/PIN), Type2(소유: 토큰/스마트카드), Type3(생체: 지문/홍채) 중 2개 이상을 쓴다.
- 원문의 프레임워크는 Spring Security, .NET, Zend, Symfony다. `[Python 적용]` Django 인증 시스템 + `LoginRequiredMixin`/`@login_required`, DRF `DEFAULT_PERMISSION_CLASSES`, Flask-Login `@login_required`, FastAPI `Depends(get_current_user)`, OTP는 `pyotp`.

**점검 질문**
- [ ] 인증이 필요한 라우트가 기본 차단(deny-by-default)인가? 예: DRF `DEFAULT_PERMISSION_CLASSES = [IsAuthenticated]`, FastAPI 라우터 단위 `dependencies=[Depends(auth)]`
- [ ] 데코레이터·의존성이 빠진 중요 엔드포인트가 없는가? (→ SEC-01)
- [ ] 관리자·결제·개인정보 기능에 2FA가 있는가?
- [ ] OTP 유효시간, 자릿수, 재사용 방지가 위 규칙을 지키는가?
- [ ] 인증서 검증(`verify=False`)을 끄거나, 역DNS 결과로 신뢰를 판단하지 않는가? (→ SEC-11, API-01)

### SR2-2. 인증 수행 제한

**설명**: 반복된 인증 시도를 제한하고 인증 실패 이력을 추적하도록 설계한다.

**요구사항 (원문)**
1. 로그인 기능 구현 시 인증시도 횟수를 제한하고, 초과 시도에 인증제한 정책을 적용해야 한다.
2. 실패한 인증시도 정보를 로깅해 추적할 수 있어야 한다.

**설계 시 고려사항**
- 로그인 시도는 **3~5회 이내**로 제한하고, 초과하면 추가 입력값(CAPTCHA 등)을 요구하거나 계정을 잠근다.
- 사용자 테이블에 로그인 실패 횟수, 계정 잠금 여부, 마지막 성공·실패 로그인 시간, 로그아웃 시간을 저장하도록 설계한다. 사용자ID별·세션ID별로 추적한다.
- 자동입력 방지문자(reCAPTCHA 등)를 둔다.
- 반복 실패에 대한 로깅 정책을 정하고, 로그로 허용되지 않은 로그인 시도를 분석할 수 있게 한다.
- `[Python 적용]` `django-axes`, Flask-Limiter, `slowapi`(FastAPI), Redis 기반 카운터.

**점검 질문**
- [ ] 로그인·OTP 검증·비밀번호 재설정 엔드포인트에 시도 횟수 제한이나 rate limit이 있는가? (→ SEC-16)
- [ ] 실패 로그에 사용자ID, 시각, IP가 남고, **비밀번호 원문은 남지 않는가**?

### SR2-3. 비밀번호 관리

**설명**: 생성규칙, 저장방법, 변경주기 등 비밀번호 관리정책별 안전한 적용방법을 설계한다.

**요구사항 (원문)**
1. 비밀번호 설정 시 KISA 「패스워드 선택 및 이용 안내서」의 보안 지침을 적용한다.
2. 네트워크로 비밀번호를 전송할 때는 반드시 암호화하거나 암호화된 통신채널을 써야 한다.
3. 비밀번호 저장 시 **솔트가 적용된 안전한 해시함수**를 쓰고, 해시는 **서버에서** 실행해야 한다.
4. 비밀번호 재설정·변경 시 안전하게 바꿀 수 있는 규칙을 정해 적용해야 한다.
5. 비밀번호 관리 규칙을 정해 적용해야 한다.

**설계 시 고려사항**
- 안전한 패스워드 (원문 표 3-12):
  - 두 종류 이상 문자 조합이면 **8자리 이상**, 또는 **10자리 이상** 문자열 (문자 종류: 영대문자·영소문자·특수문자·숫자 4가지. 숫자로만 구성하면 취약할 수 있음)
- 안전하지 않은 패스워드: 같은 문자 반복(`123123`), 키보드 연속 문자열(`qwerty`), 숫자가 맨 앞/뒤에만 오는 구성(`1security`), 가족·이름·생일·주소·전화번호 등 개인정보, 이용자 ID 포함(`kisa1`), 사전 단어(`love12`), 유명 인물·사이트·기업명, 비슷한 문자 치환(`O→0`, `I→1`), 시스템 초기·예제 패스워드, 한글/영문 발음 치환형.
- 전송: TLS 최신 버전(TLS 1.2, 1.3)만 지원하고, KISA 「암호 알고리즘 및 키 길이 이용 안내서」의 안전한 알고리즘 조합을 쓴다.
- 저장: 일방향 해시 + **사용자별 고유 솔트(32바이트 이상 권장)**. 단순 SHA-256은 빠른 연산과 동일 입력→동일 출력 문제로 부족하다. `[Python 적용]` Django 기본 `PBKDF2PasswordHasher` 또는 `Argon2PasswordHasher`, `argon2-cffi`, `bcrypt`, `hashlib.scrypt`, `hashlib.pbkdf2_hmac`(반복 횟수 충분히).
- 변경: 이전에 쓰지 않은 새 비밀번호여야 하고 이전 비밀번호와 연관성이 없어야 한다.
- 재설정: "비밀번호 찾기"는 이메일·질의응답으로 **해당 사용자에게만** 전달하고, 올바른 비밀번호가 입력되기 전에는 이메일 등 개인정보를 수정할 수 없게 한다. 질의응답이 일정 횟수 이상 틀리면 기능을 막는다. 기존 비밀번호를 알려주지 말고 **임시 비밀번호**를 발급하며, 사용자는 발급 즉시 새 비밀번호로 바꿔야 한다. (원문 사고사례: 이름·아이디·이메일만 알면 다른 메일주소로 임시 비밀번호를 받을 수 있었던 사례)
- 관리 규칙: 변경주기 3개월(또는 6개월), 만료기간 설정(만료 시 로그인하면 변경 요청, 변경 시 주기 초기화), 마지막 성공 로그인 시간 저장·사용자에게 표시, 시스템 초기 비밀번호는 설치 즉시 변경.

**점검 질문**
- [ ] 회원가입·비밀번호 변경 시 서버 측에서 길이·조합·금지패턴 검증을 하는가? (Django `AUTH_PASSWORD_VALIDATORS` 설정 확인) (→ SEC-09)
- [ ] 비밀번호가 평문, 가역 암호화, MD5/SHA1/솔트 없는 SHA-256으로 저장되지 않는가? (→ SEC-14, SEC-04)
- [ ] 클라이언트(JS)에서 해시한 값을 그대로 저장·비교하지 않는가?
- [ ] 비밀번호·DB 접속정보가 소스코드에 하드코딩되어 있지 않은가? (→ SEC-06)
- [ ] 재설정 토큰이 충분히 랜덤하고(`secrets`), 1회용이며, 만료시간이 있는가?
- [ ] 비밀번호 변경 시 이전 비밀번호 확인과 기존 세션 무효화가 있는가?

### SR2-4. 중요자원 접근통제

**설명**: 중요자원(프로그램 설정, 민감한 사용자 데이터 등)을 정의하고, 신뢰할 수 있는 접근통제 방법(권한관리 포함)과 실패 시 처리방법을 설계한다.

**요구사항 (원문)**
1. 중요자원에 대한 접근통제 정책을 수립해 적용해야 한다.
2. 중요기능에 대한 접근통제 정책을 수립해 적용해야 한다.
3. 관리자 페이지에 대한 접근통제 정책을 수립해 적용해야 한다.

**설계 시 고려사항**
- **RBAC**(역할기반 접근제어)로 역할에 따라 권한을 부여하고, 자원에는 **ACL**(접근제어목록)을 구성한다.
- ACL 적용 시 원문의 3가지 기능: (1) 도메인 객체의 ACL 항목 조회·수정, (2) **메소드 호출 전** 객체 작업 권한 검증, (3) **메소드 호출 후** 반환 객체 권한 검증.
- 중요자원: 접근권한은 최소권한으로, 사용자·그룹별 접근을 확인한다. **최소권한 원칙과 권한분리** 정책에 따라 할당하고, 요구조건을 충족할 때만 허가한다.
- 중요기능: 익명·일반·특권사용자·관리자 영역을 구분하고 RBAC·비즈니스 로직에 따라 통제한다. 권한 할당·수정·확인을 프로그램에서 수행해 의도치 않은 권한 획득을 막는다. 파라미터 변조 여부를 확인한다. 상위권한 작업은 **권한상승을 가능한 마지막에 하고 끝나면 즉시 원복**한다.
- 관리자 페이지: URL을 쉽게 추측할 수 없게 하고(`/admin` 기본 경로 회피), TLS를 쓰고, 접속 IP를 제한하고 80번이 아닌 별도 포트를 쓰며, 접속 시 추가인증을 요구한다.
- 원문 사고사례: 고유번호 9자리를 자동 대입해 다른 고객 정보를 조회(IDOR), 디렉토리 리스팅 노출.
- `[Python 적용]` Django `permission_required`, `has_object_permission`(DRF), `django-guardian`(객체 권한), `casbin`, 쿼리를 항상 `owner=request.user`로 범위 제한.

**점검 질문**
- [ ] 객체 조회·수정·삭제 시 URL/파라미터 ID만으로 접근하지 않고 소유자·권한을 확인하는가? (IDOR) (→ SEC-02)
- [ ] Django admin 경로가 기본 `/admin/`이 아니며, IP 제한·2FA가 있는가?
- [ ] `os.chmod(..., 0o777)`, `os.umask(0)`, 전역 읽기·쓰기 권한으로 파일을 만들지 않는가? (→ SEC-03)
- [ ] 정적 파일 서버에서 디렉토리 리스팅이 꺼져 있는가?
- [ ] 권한 상승(`os.setuid`, `sudo` 호출)이 필요한 코드가 범위를 최소화하고 원복하는가?

### SR2-5. 암호키 관리

**설명**: 암호키 생성, 분배, 접근, 파기 등 생명주기별 관리방법을 안전하게 설계한다.

**요구사항 (원문)**
1. DB 데이터 암호화에 쓰는 암호키는 KISA 「암호이용안내서」(본문: 「암호 키 관리 안내서」)의 방법을 적용해야 한다.
2. 설정파일 내 중요정보 암호화에 쓰는 암호키는 **암호화해서 별도 디렉토리**에 보관해야 한다.

**설계 시 고려사항**
- 키 관리 규칙: (1) DB 암호화 키는 DB와 **물리적으로 분리된 곳**에 보관, (2) 생성·분배·사용·폐기 생명주기 정책을 명시, (3) 패스워드·암호키는 메모리에 저장하지 않음, (4) 불가피하면 사용 후 메모리를 0으로 초기화, (5) 키 생성·변경 시 백업 기능 구현, (6) 키 종류별 유효기한 설정.
- 조직 보호 목적에 맞게 FIPS 140-2 레벨(1~4)을 채택한다.
- 생명주기 프로세스: 생성(누가, 어떤 프로그램으로), 사용(방법, 키 종류별 변경주기, 인가된 사용자만 접근), 폐기(사용주기 종료·용도 종료 시 안전한 폐기 절차).
- 키 복구: 퇴사 등으로 본인 이외의 복구가 필요하면 정보보호담당자 관리하에 키 관리대장에서 복구한다.
- 키 사용 유효기간 (NIST 권고, 원문 표 3-17): 대칭키 송신자 사용기간 최대 2년 / 수신자 (송신자 기간+3년) 이하, 암호화 공개키·복호화 개인키 최대 2년, 서명용 개인키 1~3년, 검증용 공개키는 키 크기에 따라 다름. 기간이 지나면 UI로 알리고 새 키 생성을 권장한다.
- 설정파일 내 중요정보를 암호화한 키는 **마스터키로 암호화**해 별도 디렉토리에 보관한다.
- `[Python 적용]` 키는 환경변수·시크릿 매니저(AWS KMS/Secrets Manager, GCP Secret Manager, HashiCorp Vault)로 주입하고, `.env`는 저장소에 커밋하지 않는다(`.gitignore`). Django `SECRET_KEY`, Flask `SECRET_KEY`도 암호키로 취급한다.

**점검 질문**
- [ ] `SECRET_KEY`, AES 키, JWT 서명키, API 키가 코드·설정파일에 하드코딩되어 있지 않은가? (→ SEC-06)
- [ ] 주석에 키·비밀번호·내부 IP 등 주요정보가 남아 있지 않은가? (→ SEC-13)
- [ ] `.env`, `*.pem`, `*.key`, `credentials.json`이 저장소에 포함되어 있지 않은가?
- [ ] 키 교체(rotation) 방법이 있는가? (예: Django `SECRET_KEY_FALLBACKS`)

### SR2-6. 암호연산

**설명**: 국제표준 또는 검증필 암호모듈로 등재된 안전한 알고리즘을 선정하고, 충분한 키 길이·솔트·난수를 적용한 암호연산 방법을 설계한다.

**요구사항 (원문)**
1. 대칭키·비대칭키 암호화 시 KISA 「암호이용안내서」의 알고리즘과 안전성이 보장되는 키 길이를 써야 한다.
2. 복호화되지 않는 암호화(해시)를 쓸 때는 안전한 해시 알고리즘과 솔트를 적용해야 한다.
3. 난수 생성 시 안전한 난수 생성 알고리즘을 써야 한다.

**설계 시 고려사항**
- base64 같은 단순 인코딩은 암호화가 아니다 (원문 사례1).
- 키 길이 (원문 표 3-18, NIST 알고리즘 안전성 유지기간 및 최소 키 길이 권고):

  | 안전성 유지기간 | 보안강도 | 대칭키 | RSA(인수분해) | 이산대수 공개키 | 이산대수 개인키 | ECC |
  |---|---|---|---|---|---|---|
  | 2011~2030년 | 112 | 112 | 2048 | 2048 | 224 | 224 |
  | 2030년 이후 | 128 | 128 | 3072 | 3072 | 256 | 256 |
  | 2030년 이후 | 192 | 192 | 7680 | 7680 | 384 | 384 |
  | 2030년 이후 | 256 | 256 | 15360 | 15360 | 512 | 512 |

  - `[Python 적용]` 실무 기준: AES-128 이상(권장 AES-256), RSA 2048 이상(2030년 이후를 고려하면 3072), ECC 224비트 이상(실무상 P-256 이상).
- 권고 알고리즘 (원문 표 3-19):
  - 블록암호: 국내(2018) SEED, HIGHT, ARIA, LEA / NIST(2015) AES, 3TDEA
  - 해시: 국내 SHA-224/256/384/512, SHA-512/224, SHA-512/256, SHA3-224/256/384/512, LSH-224/256/384/512, LSH-512/224, LSH-512/256 / NIST는 LSH 제외 동일
  - 키 공유: DH, ECDH (NIST: + MQV, ECMQV)
  - 공개키 암·복호화: RSAES (NIST: RSA)
  - 전자서명: RSA-PSS, KCDSA, ECDSA, EC-KCDSA (NIST: RSA, DSA, ECDSA)
- 해시 함수는 사용목적(메시지인증/키 유도/난수생성용, 단순 해시/전자서명용)과 보안강도에 따라 선택한다.
- 난수: FIPS 140-2 인증 암호모듈의 난수생성기와 256비트 이상의 시드를 쓴다. `[Python 적용]` `secrets`, `os.urandom`, `random.SystemRandom`. `random` 모듈은 보안 용도 금지.
- `[Python 적용]` 암호화 라이브러리는 `cryptography`(AES-GCM, `Fernet`)를 쓰고, 유지보수가 끝난 `pycrypto`는 쓰지 않는다(필요하면 `pycryptodome`). ECB 모드, 고정 IV/nonce 금지.

**점검 질문**
- [ ] DES, 3DES(신규), RC2, RC4, Blowfish, MD5, SHA1, ECB 모드 사용이 없는가? (→ SEC-04)
- [ ] RSA 키가 2048비트 이상, 대칭키가 128비트 이상인가? (→ SEC-07)
- [ ] 토큰·세션ID·비밀번호 재설정 코드·OTP·솔트를 `random` 모듈로 만들지 않는가? (→ SEC-08)
- [ ] 해시에 솔트를 쓰는가? (→ SEC-14)
- [ ] TLS 클라이언트에서 인증서 검증을 끄지 않는가? (→ SEC-11)

### SR2-7. 중요정보 저장

**설명**: 중요정보(비밀번호, 개인정보 등)를 저장·보관하는 방법이 안전하도록 설계한다.

**요구사항 (원문)**
1. 중요정보나 개인정보는 암호화해서 저장해야 한다.
2. 불필요하거나 쓰지 않는 중요정보가 메모리에 남지 않도록 해야 한다.

**설계 시 고려사항**
- 중요정보를 다루는 "안전영역"을 정하고 그 밖으로 새지 않게 한다.
- 서버 DB·파일에 저장하는 중요정보는 반드시 암호화하고, SR2-6의 알고리즘과 키를 쓴다.
- **쿠키, HTML5 로컬저장소** 같은 클라이언트 측 저장소에는 중요정보를 저장하지 않는다. 부득이하면 암호화한다.
- HTML은 사용자에게 공개된 것과 같으니 중요 로직과 주석은 서버 측에서만 처리한다.
- 더 이상 필요 없는 데이터는 메모리를 0으로 초기화한다. `[Python 적용]` `str`은 불변이라 지울 수 없으므로 민감 데이터는 `bytearray`로 다루고 사용 후 덮어쓴다. 가능한 한 수명을 짧게 한다.
- 민감 페이지는 사용자 측 캐싱을 끄는 캐시정책을 둔다 (`Cache-Control: no-store`). 부득이 캐싱하면 암호화한다.
- 인증정보 입력 폼은 자동완성을 끈다 (`autocomplete="off"`).

**점검 질문**
- [ ] 주민등록번호·계좌번호·카드번호 등 고유식별/금융정보가 평문 컬럼에 저장되지 않는가? (→ SEC-05)
- [ ] 영속 쿠키(`max_age`/`expires` 설정)에 세션ID·권한정보·개인정보를 넣지 않는가? (→ SEC-12)
- [ ] 로그·예외 메시지에 개인정보·토큰이 남지 않는가?
- [ ] 민감 응답에 `Cache-Control: no-store`가 설정되는가?

### SR2-8. 중요정보 전송

**설명**: 중요정보(비밀번호, 개인정보, 쿠키 등)를 전송하는 방법이 안전하도록 설계한다.

**요구사항 (원문)**
1. 인증정보 같은 민감정보는 안전하게 암호화해서 전송해야 한다.
2. 쿠키에 포함되는 중요정보는 암호화해서 전송해야 한다.

**설계 시 고려사항**
- 중요정보는 안전한 암호모듈로 암호화하거나 안전한 통신채널(TLS)로 전송한다.
- 클라이언트→서버(hidden 필드, Ajax 변수, 쿠키, 헤더), 서버→클라이언트(응답 헤더 등) 데이터에 **불필요하게 많은 정보**가 들어가지 않게 한다.
- 쿠키에는 중요정보를 넣지 않는 것이 원칙이다. 부득이하면 **세션쿠키**로 설정하고 암호화한다.
- `[Python 적용]` `SESSION_COOKIE_SECURE=True`, `CSRF_COOKIE_SECURE=True`, `SECURE_SSL_REDIRECT=True`, `SECURE_HSTS_SECONDS`, Flask `SESSION_COOKIE_SECURE`. `http://`로 외부 API에 중요정보를 보내지 않는다.

**점검 질문**
- [ ] 외부 API·내부 서비스 호출 URL이 `http://`가 아닌가? `smtplib.SMTP`에 `starttls()`가 있는가? `ftplib.FTP` 대신 SFTP/FTPS를 쓰는가? (→ SEC-05)
- [ ] 쿠키에 `Secure`, `HttpOnly`, `SameSite`가 설정되는가?
- [ ] API 응답에 비밀번호 해시, 내부 ID, 불필요한 개인정보가 포함되지 않는가? (직렬화 필드 확인)

## 3. 에러처리

### SR3-1. 예외처리

**설명**: 오류메시지에 중요정보(개인정보, 시스템 정보, 민감정보 등)가 노출되거나, 부적절한 에러·오류 처리로 의도치 않은 상황이 생기지 않도록 설계한다.

**요구사항 (원문)**
1. 명시적 예외는 예외처리 블록으로 예외 발생 시 수행할 기능이 구현되도록 해야 한다.
2. 런타임 예외는 입력값의 범위를 확인해 애플리케이션이 정상 동작할 수 있는 값만 쓰도록 보장해야 한다.
3. 에러가 발생하면 상세 에러 정보가 사용자에게 노출되지 않게 해야 한다.

**설계 시 고려사항**
- 언어별 예외처리 문법의 안전한 사용법을 시큐어코딩 규칙으로 정한다. 원문 예는 Java Logger API 활용이다. `[Python 적용]` `logging` 모듈 사용, `print(traceback)` 금지.
- 입력값에 따라 예외가 날 수 있으면 범위를 먼저 확인한다.
- 에러 시 지정된 에러 페이지로 보낸다. 원문 예는 `web.xml`의 `<error-page>` 404/500/Throwable 설정이다. `[Python 적용]` Django `handler404`/`handler500`과 `DEBUG=False`, Flask `@app.errorhandler(404/500/Exception)`, FastAPI `@app.exception_handler(Exception)`.
- 사용자에게 보내는 오류메시지에 중요정보가 들어가지 않게 한다. 스택트레이스·예외명 출력은 공격자가 내부 구조를 파악하는 데 쓰인다.

**점검 질문**
- [ ] 운영 설정에서 `DEBUG=False`, Flask `app.run(debug=True)` 미사용, FastAPI `debug=False`인가? (→ ENC-02, ERR-01)
- [ ] 예외 메시지(`str(e)`, `traceback.format_exc()`)를 응답 본문에 넣지 않는가? (→ ERR-01)
- [ ] `except: pass`, `except Exception: pass`처럼 오류를 무시하는 코드가 없는가? (→ ERR-02)
- [ ] 너무 넓은 `except Exception`/`except BaseException`으로 보안 실패를 삼키지 않는가? (→ ERR-03)

## 4. 세션통제

### SR4-1. 세션통제

**설명**: 다른 세션 간 데이터 공유 금지, 세션ID 노출 금지, (재)로그인 시 세션ID 변경, 세션 종료(비활성화, 유효기간 등) 처리 등 세션을 안전하게 관리하는 방안을 설계한다.

**요구사항 (원문)**
1. 세션 간 데이터가 공유되지 않도록 설계해야 한다.
2. 세션이 안전하게 관리되도록 해야 한다.
3. 세션ID가 안전하게 관리되도록 해야 한다.

**설계 시 고려사항**
- 세션 간 공유 금지: 스레드로 동작하는 컨트롤러나 싱글톤 서비스 컴포넌트의 **클래스 멤버변수·클래스 변수**는 세션 간에 공유되므로, 읽고 쓰는 변수를 두지 않는다. `[Python 적용]` 모듈 전역 변수, 클래스 속성, 요청 간 재사용되는 객체에 사용자별 데이터를 저장하지 않는다. 요청 범위 데이터는 Flask `g`, `contextvars`, Django `request`에 둔다.
- 세션 관리:
  - 모든 페이지에서 로그아웃할 수 있게 하고, 로그아웃 시 세션을 완전히 제거하는 API를 쓴다 (원문: Java `session.invalidate()`. `[Python 적용]` Django `logout()`/`request.session.flush()`, Flask `session.clear()` + 서버 측 세션 삭제).
  - 세션 타임아웃은 **중요기능 2~5분, 위험도가 낮으면 15~30분**으로 한다. 이전 세션이 끝나지 않은 상태에서 새 세션이 생기지 않게 한다.
  - 브라우저 종료는 서버가 알 수 없으므로, 일정 시간 쓰지 않은 세션은 강제로 삭제한다.
  - 중복 로그인을 허용하지 않으면, 새 로그인 시 이전 세션을 끝내거나 새 연결을 막는 정책을 둔다.
  - 세션ID 쿠키에 **HttpOnly**를 설정한다.
  - 비밀번호 변경 시 활성 세션을 삭제하고 다시 할당한다.
- 세션ID 관리:
  - 생성: 안전한 서버에서 만들고, **최소 128비트**, 안전한 난수로 예측 불가능하게 한다.
  - 사용: URL Rewrite로 세션ID가 URL에 노출되지 않게 한다.
  - 폐기: **로그인 성공 시 기존 세션ID를 파기하고 재발급**(세션 고정 공격 대응)한다. 장시간 접속 시 주기적으로 재할당한다.

**점검 질문**
- [ ] 모듈 전역·클래스 변수에 현재 사용자, 요청 데이터를 저장하는 코드가 없는가? (→ ENC-01)
- [ ] 로그인 성공 후 세션 재발급이 있는가? (Django `login()`은 자동 `cycle_key()`. Flask 기본 쿠키 세션은 재발급 개념이 없으므로 `session.clear()` 후 재설정하거나 서버 측 세션 사용)
- [ ] `SESSION_COOKIE_AGE`, `PERMANENT_SESSION_LIFETIME`이 기능 위험도에 맞게 짧은가?
- [ ] `SESSION_COOKIE_HTTPONLY=True`, `SESSION_COOKIE_SECURE=True`인가?
- [ ] 세션ID·토큰이 URL 쿼리스트링에 실리지 않는가?
- [ ] 비밀번호 변경 시 다른 세션이 무효화되는가? (Django `update_session_auth_hash` 사용 여부와 정책 확인)
