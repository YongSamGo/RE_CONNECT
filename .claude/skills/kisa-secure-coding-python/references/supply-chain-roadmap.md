# A부. 원문 정리

## A1. 추진 배경 (Chapter 1, p.1)

| 배경 | 내용 |
|---|---|
| SW 활용 확대 | AI·클라우드·IoT 일상화로 SW가 제조·교통·의료 등 모든 산업과 일상에 융합 |
| 공급망 복잡화와 위협 고도화 | 공개SW·타사SW·제3자 협력 개발로 공급망 확대·복잡화. **광범위한 취약점 탐지와 빠른 공격 속도가 특징인 AI 기반 공격**이 공급망 공격에 쓰이면 기존 체계로 대응에 한계. 한 번의 공격으로 수많은 기업·개인에 영향 |
| 정책 패러다임 변화 | 美·EU는 개발·공급자 책임 강화와 지속적 사후관리 등 '사이버 복원력' 정책 추진. 인증 요건 추가·검증 제품만 납품 → 국내 기업 무역장벽 우려 |

## A2. 현황 및 위협 분석 (Chapter 2, p.2~4)

**1. 개발·공급 환경 변화**

- 자체 개발보다 외부 개발 SW(공개 SW, 제3자 개발 SW)를 적극 활용 → 수직적 공급망이 복잡하고 상호 의존적인 구조로 변화
- 검증 없는 외부 SW 활용은 개발 주체 불명확, 관리 책임 문제, 공급망 위협으로 이어짐
- **공개 SW와 AI 모델이 생성한 코드**는 누구나 접근할 수 있어 공격자가 취약점을 발견·악용할 위험이 높다 (원문 p.2 주석)
- 참고 수치: '25년 전 세계 생성형 AI 서비스 지출 전년 대비 76.4% 증가 전망(가트너), AI 도구·오픈소스 활용 통계(OSSRA 2024)

**2. 고도화되는 공급망 공격**

- 부실한 보안 관리 악용 → 공급망의 보안 허점을 노리는 공격으로 이동. '망 중심' 경계 보안으로는 초기 탐지·예방에 한계
- 상대적으로 관리가 취약한 **공개 SW와 중소 개발 협력사**를 노린 공격 기승
- 사이버공격 지속 기간 평균 253일(카스퍼스키 '24) → 초기 탐지 어려움
- 공급망 공격 글로벌 피해액 2023년 460억 달러 → 2031년 1,380억 달러 추정(가트너 '24.6)

**3. 주요국 정책·제도 (p.4)**

| 국가 | 분야 | 내용 |
|---|---|---|
| 미국 | 정부 납품 SW | 안전한 개발 증명(Secure SW Development Attestation Form, '23.6~), 연방기관에 SP 800-161r1 공급망 위험관리 준수 요구('25.1~) |
| 미국 | 의료(FDA) | 인허가 시 안전한 제품 개발 보안 체계(SPDF) 또는 QS 규정 준수 요구('23.11 시행) |
| EU | 디지털 요소가 포함된 제품 | 사이버복원력법(CRA): 제조·수입·판매업체별 공급망 보안 규정, 지속적 관리·감독('27.12 시행 예정, '24.12 공포) |

- SW 개발·공급기업 책임 강화, **SBOM을 활용한 추적·관리 의무화** — 출시 후 침해사고·취약점 발생 시 보완·수정 업데이트 배포 등 즉각 조치 요구
- 기업 현장 사례: FDA 인허가에서 SBOM 요구, 美 연방 납품 기업이 SBOM 관리요건 미충족 시 차년도 계약 불가 통보, 글로벌 금융기업 납품 무산

## A3. 시사점 및 추진 방향 (Chapter 3, p.5)

| 시사점 | 방향 |
|---|---|
| 운영 단계에서 개발·공급 단계로 확장되는 위협 | 기획부터 유지보수까지 공급망 全단계 보안 |
| 초기 탐지가 어렵고 연쇄 피해로 이어짐 | 공급망 투명성 확보, 사고 복원력 강화 |
| 주요국 제도화 | 국내 환경에 맞는 민·관 협력체계·제도 개선 |

| 단계 | 현황 및 문제점 | 대응 방향 |
|---|---|---|
| 개발·공급 | 개발 단계를 노린 공격에 취약 | 개발·공급기업의 보안 내재화 지원 |
| | 복잡해진 SW 공급망 위협 증가 | SBOM을 활용한 공급망 투명성 확보 |
| | 보안을 고려하지 않는 기능·성능 중심 개발 관행 | 보안 중심 개발문화 정착 |
| 피해 확산 방지 | 초기 탐지의 어려움 | 위협정보 발굴 체계 다각화 |
| | 2차 피해로 연쇄 확산 | 공급망 참여자 간 보안정보 공유·협력체계 |
| 공급망 보안 기반 | 공급망 보안 관련 기준 부재 | 공급망 보안 원칙 수립 및 가이드라인 개발 |
| | 전문인력 부족 | 정보보호 전문인력의 공급망 보안 역량 강화 |
| | 시험·점검 환경 부재 | 공급망 보안 테스트베드 조성 |

추진 방향 3가지

- **(예방)** 안전하게 개발하고 책임 있게 공급할 수 있는 보안 내재화 촉진
- **(복원)** 공급망 가시화를 통한 신속한 복구·대응 체계 마련
- **(기반)** 사이버 복원력 확보를 위한 정책적·제도적 기반 조성

## A5. 비전 및 추진전략 (Chapter 4, p.8)

- **비전**: 안전하고 책임 있는 공급망 보안 체계의 전환을 통한 사이버 복원력 확보
- **목표**
  - 역량 강화: SW 공급망 보안 및 위험관리 모델 확보, 전문 기술·인력 양성
  - 체계 마련: 민간·공공의 유기적인 공급망 위협 정보 공유, 선제적 피해확산 차단
  - 기반 조성: 일관성 있는 SW 공급망 보안 정책·제도 운영, 국제협력·공조 체계 구축

### RM 판정 기준

- **RM-01**: 그림5의 12개 활동 중 저장소 증거가 있는 수로 판정 (9개 이상 준비됨, 4~8개 일부 준비, 3개 이하 미준비). 활동마다 근거 파일을 적는다.
- **RM-03**: SAST·SCA·비밀 스캔 3종이 PR에서 자동 실행되면 준비됨.
- **RM-04**: 릴리스마다 SBOM 생성 + 필드 검증 + 취약점 스캔이 자동이면 준비됨, 수동 생성 파일만 있으면 일부 준비.
- **RM-05**: 취약점이 남아 있는 상태의 스캔 결과·SBOM(취약점 포함)이 공개 저장소에 커밋되어 있으면 미준비 — 공격자에게 목록을 주는 셈 (가이드라인 A16-마). CI 아티팩트(접근 제한)로 옮기도록 권고.
- **RM-07**: SECURITY.md에 비공개 신고 경로(이메일, GitHub Private vulnerability reporting)가 있으면 준비됨. 공개 이슈로만 신고받게 하면 일부 준비.
- **RM-08**: 지원 버전·지원 종료 시점이 공개되어 있으면 준비됨.
- **RM-09**: pip-audit(PyPI/OSV)·osv-scanner처럼 NVD 외 DB를 쓰는 도구가 있으면 준비됨.
- **RM-10**: `--ignore-vuln`·`.trivyignore` 등 무시 목록에 사유·검토일이 없으면 미준비. VEX 문서나 사유 주석이 있으면 준비됨.
- **RM-11**
  - `trust_remote_code=True`, `revision` 고정 없는 `from_pretrained`, `torch.load`/pickle 기반 가중치 로드는 COD-05·SCP-15와 함께 지적 (모델 저장소 변경·악성 가중치 위험).
  - 모델·데이터셋의 출처·라이선스·해시를 README 또는 모델 카드에 기록했으면 준비됨.
  - AI 코딩 도구로 생성한 코드가 있으면 일반 코드와 같은 리뷰·정적 분석을 거치는지(PR 리뷰 규칙) 확인.
- **RM-12**: 공공·국방 납품 대상이 아니면 `해당없음`. 대상이면 외부 SDK·장비 연동 모듈의 제조사·원산지·제재 여부 목록이 있는지 본다 (체크리스트 세부는 '27 이후 발표 예정).
